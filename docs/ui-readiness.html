UI Readiness Register

What the current backend can serve for the Living Software Understanding System spec, what still needs building, and what cannot be built honestly yet.

The schema is about one layer ahead of the extractors, and the server is about one layer behind the schema. types.ts already models nearly everything the spec describes — journeys, branching transitions, outcomes, evidence, provenance, confidence. The extractors mostly do not produce it, and the server can neither store nor query it. Building the UI today would yield a convincing Overview, Code and Impact experience alongside five dead tabs.

Structural blockers

BLOCKER No queryable entity model

The backend stores one JSONB blob per project across two tables — graphs and annotations — and exposes eight endpoints, all graph-level CRUD. There is no projection, search, trail, coverage, or change endpoint.

computeProjection, the model-to-UI boundary the architecture rests on, runs client-side only and has no HTTP surface. Every route in the spec needs addressable entities, per-entity projections, cross-entity search, versioned snapshots, and durable per-user state. None of that is expressible over a document that must be loaded whole.

BLOCKER Five lenses have no data source

Behavior has no extractor for conditionals, error handlers or state transitions, and OutcomeKind has zero producers. Journeys only ever come from hand-authored linear paths. Why cannot work at all because .md is rejected at the file-read boundary, so ADRs and docs are never read. Runtime has no telemetry source. Tests are deliberately excluded by SKIP_FILE_PATTERNS.

BLOCKER Trails do not exist

The spec's central concept requires each step to preserve focus, lens, depth, question, notes and timestamp, and trails to be saved, replayed, shared, forked, annotated and detected as stale. Today ExplorationQuery.trail is an array of node ids used for scoring and never persisted; in-app navigation history is a React ref that dies on reload.

The cheapest win, in detail

The OpenAPI importer considers only success codes. The spec you already parse declares 56 error responses that map almost directly onto OutcomeKind.

importer reads ['200','201','202','203','204'] catalog.ts:472 spec declares 21 × 401 → permission_denied 11 × 422 → validation_error 11 × 400 → validation_error 9 × 404 → not_found 4 × 412 → conflict

The emptiest and most novel lens in the product has real, code-derived outcome data sitting unread in a file the importer already opens. This is the best ratio of value to effort in the register.

What is genuinely ready

Measured, not assumed — these run against the real repository today.

  • Projection engine. Focus, altitude, lens and trail resolve to ranked entities with explanations, budgets, diversity selection and honest notices. Hub-dampening and diversity are mutation-verified.
  • Semantic zoom. Six altitude tiers with coverage counts and loud degradation when a tier is empty — product 1, domain 10, behavior 50, system 120, implementation 483, code 0.
  • Impact. Weighted blast radius, upstream and downstream.
  • Extraction. OpenAPI, file-level codebase, Go backend, transitive API linking and git history — 646 nodes, roughly 1,700 links, 3% isolated.
  • Merge and diff. Non-destructive, override-aware, deterministic; diff now covers journeys.

Known traps

  • Three backend importers are stubs. nodejs.ts, python.ts and rust.ts return unsupported_language in fourteen lines. The Node plugin declares .js .mjs .cjs .ts, so a JavaScript-dominant tree dispatches to a stub and silently yields nothing.
  • Health is declared and consumed nowhere. Dead field in types.ts.
  • Name collision on "lens". src/schema/entity/lens.ts means entity-scoped subgraph filtering, unrelated to the spec's lenses. Worth resolving before UI work begins.
  • Deep links need redefining. ViewState encodes the retired 3D graph's camera and selection, not focus, lens, altitude and trail.
  • The code altitude is empty because extraction is file-level. Deliberately deferred after review: the pathology concentrates in a single file, and a regex symbol extractor misses exports in 47% of files.

Sequence before building the UI

Ordered by dependency — each step makes the next one worth doing.

  1. Read what is already on disk

    OpenAPI error responses, test files, and markdown. Turns three dead lenses into partially populated ones without any new data source.

  2. Hand-author one branching journey

    Deposit or bonus claim, wired to real node ids. The only way Behavior and Journey get exercised, and what the prototype was always meant to test.

  3. Add a projection endpoint and trail persistence

    The minimum server surface any route in the spec requires.

  4. Then build the UI

    Against a backend that can answer the questions the interface asks of it.

Every claim was verified against source rather than inferred from documentation. Figures come from running the full pipeline against casino-frontend: 731 source files, a 4,243-line OpenAPI spec, 580 commits.
