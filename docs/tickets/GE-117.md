# GE-117 — DB schema importer as catalog source (deferred)

**Status:** TODO (post-demo)
**Phase:** Ecosystem
**Effort:** L
**Depends on:** GE-115 (catalog shape), GE-115b (propagation)
**Blocks:** —

## Summary

Import a database schema (Postgres DDL, Prisma schema, or Drizzle schema) and seed the entity catalog from the tables. DB-backed entities that don't surface via OpenAPI (internal tables, joins, derived views) get first-class catalog entries. Deferred — the OpenAPI-only catalog is enough for the demo.

## Context

OpenAPI gives us the public-API view of the entity universe. For apps with rich internal data models, that's a subset — internal reporting tables, event logs, audit tables, join tables are invisible. A direct DB parse gives the authoritative list.

Three parseable sources, in order of unambiguous-ness:

1. **Drizzle schema (TypeScript)** — direct mapping: `pgTable('payments', { … })` → entity `payment`. We already use Drizzle for the graph explorer's own persistence (see `db/client.ts`); the parser would read the same shape.
2. **Prisma schema (`.prisma`)** — `model Payment { … }` → entity `payment`. Well-structured, deterministic.
3. **Raw Postgres DDL** — `CREATE TABLE payments (…)` → entity `payment`. Needs SQL tokenizer. Most brittle.

The MVP demo (admin-dashboard) ships Drizzle at the persistence layer but its application entities come from a Go backend that uses its own ORM. Not worth a parser for one demo target.

## Scope

When the user clicks "Import DB schema" (new dialog entry alongside OpenAPI and codebase):

- Paste-or-upload a Drizzle / Prisma / SQL file.
- Auto-detect format (Drizzle: `pgTable(` patterns; Prisma: `model X {` patterns; SQL: `CREATE TABLE` patterns).
- Parse tables. For each table:
  - Table name → normalize via GE-115's normalization (singularize, kebab-case, strip prefixes).
  - Columns with foreign keys → create `data_flow` links between the resulting database nodes (`orders.user_id → users.id` → link).
  - Column types → store on node metadata but don't render.
- Merge into the graph:
  - If a catalog entity of the same name already exists (from OpenAPI), unify — don't duplicate. The DB import becomes a confirming signal.
  - If it's new, add to `meta.entities` and create a `database`-type node.
- Mark new nodes as `origin: 'auto:db'`. Extend the `Origin` type.
- Run GE-115b propagation after merge.

### Normalization extras

- Plural table names (`payments`, `users`, `bonus_issues`) singularize to their entity form.
- Drizzle/Prisma include column nullability and types — skip for MVP but lay down the extension point (could fuel a "schema drift" feature later).
- Foreign keys become data_flow edges. Many-to-many join tables (no non-FK columns) don't get their own node — render as a direct edge between the two endpoints.

### UI

- New dialog: `DBSchemaImportDialog.tsx`. Same pattern as `ImportDialog.tsx` (OpenAPI) and `CodebaseImportDialog.tsx`.
- Placement in the toolbar: next to the existing import buttons.
- Progress indicator during parse (bigger schemas can take a moment).

## Out of scope

- Live DB connection (pointing at a running Postgres). Paste / upload only. Live sync is GE-025-territory.
- Index definitions, constraints, triggers — domain metadata beyond tables/columns/FKs. Revisit if users ask.
- Materialized views, stored procedures, functions. Same.
- Reverse-engineering: given the graph, generate a DDL export. Future if ever.

## Acceptance criteria

- Paste a Drizzle schema. Every table appears as a database node. FKs are links.
- Table name `payments` → entity `payment`. Unified with existing OpenAPI-sourced `payment` entity (no duplication).
- Internal tables (`audit_log`, `event_outbox`) that don't appear in the OpenAPI spec show up as new catalog entries.
- Unsupported formats return a clear error ("Couldn't detect schema format — we support Drizzle TS, Prisma, and SQL CREATE TABLE statements").
- Re-importing the same schema is a no-op after merge (deterministic IDs).

## Risks

- **Parser brittleness**: Drizzle and Prisma have multiple API surface styles. Stay conservative — handle the 90% cases, clearly error on the rest rather than silently mis-parse.
- **Identity drift**: a table `player_accounts` (DB) vs a schema `Account` (OpenAPI) are conceptually the same but normalize differently. The review dialog's merge action covers reconciliation.
- **Scope creep**: "DB schema importer" is the doorway to a much bigger features set (schema diff, migration planner, etc.). Keep GE-117 narrow: parse, merge, done.

## Notes for the implementer

Mirror the structure of `src/importers/openapi/` — a `src/importers/database/` folder with `index.ts` (dispatcher), `drizzle.ts`, `prisma.ts`, `sql.ts`. Each returns the same shape: `{ nodes: Node[], links: Link[], warnings: Warning[] }`. The outer `index.ts` handles format detection.

Use a plain regex-based tokenizer for Drizzle/Prisma — no AST dependency. For SQL, consider `pgsql-ast-parser` if regex gets too brittle, but first try without.

Reuse GE-115's `normalizeSchemaName` directly — consistency between OpenAPI and DB naming is the whole point.
