# GE-017 — AI-generated node descriptions

**Status:** DONE
**Phase:** Phase 2 — Intelligence
**Effort:** S
**Depends on:** GE-003
**Blocks:** —

## Summary

On demand, feed a node's structural context (its name, type, connections, and neighbor names) to an LLM and receive a plain-English description that the user can accept, edit, or discard.

## Context

A graph is only as useful as its descriptions. Auto-imported nodes (from OpenAPI) come with minimal descriptions; manually added nodes often have blank descriptions because the author did not have time. An AI pass closes the gap at zero cost to the user.

Scope is intentionally minimal — this is a single-button feature, not a full AI assistant. The LLM proposes; the human decides.

## Scope

- Button on a node's detail panel: "Suggest description."
- Clicking the button assembles a prompt containing:
  - The node's name, type, and group.
  - Its direct neighbors (name, type, link label, link direction).
  - Any existing description as context.
- The prompt is sent to an LLM (Claude API, or configurable provider) via a lightweight server-side proxy or a direct client-side call if API keys are handled safely.
- The response streams into a preview area. The user can accept (replacing the current description), edit (accept with modifications), or discard.
- Accepted descriptions set `origin: "manual"` on the field (the user reviewed and chose the text — it is no longer a pure AI artifact).

## Out of scope

- Bulk generation across all nodes. Single-node only for MVP.
- AI authoring of links, paths, or annotations. Nodes only for MVP.
- Multi-turn refinement ("make it shorter", "mention latency"). Single shot — user edits manually if they want changes.
- Custom prompt templates per team. Use a fixed prompt for MVP.
- Non-LLM sources (static templates, dictionary lookups).

## Acceptance criteria

- A user can click the suggest button on any node and receive a generated description within a few seconds.
- The preview is clearly distinguishable from the accepted description (different styling, explicit accept/discard actions).
- Accepting replaces the description in the working schema.
- Editing the generated text before accepting works as expected.
- API errors (rate limit, missing key, network) surface cleanly without crashing the UI.
- The API key is not hardcoded and has a documented configuration path (env var, config file, or server proxy).

## Risks

- Prompt quality determines usefulness. A bad prompt produces generic text. Iterate on the prompt against real nodes before closing.
- Cost — bulk use is expensive, and users may spam the button. Consider a per-session rate limit.
- Security — if API keys are exposed client-side, they will leak. Document the intended deployment model (server proxy recommended) and do not ship a version that embeds keys in the bundle.

## Notes for the implementer

Keep the prompt short, structured, and deterministic. The more scaffolding you give the model (node context, neighbor context, desired length), the better and more consistent the output. Save a handful of high-quality prompt examples as test fixtures.
