# GE-023 — Multi-user annotations

**Status:** DONE
**Phase:** Phase 3 — Scale
**Effort:** M
**Depends on:** GE-003, GE-020
**Blocks:** —

## Summary

Team members can attach comments to nodes and links. Annotations are stored server-side, attributed to the author, and visible to other users with access to the graph.

## Context

A graph alone does not hold institutional knowledge — the knowledge is the annotations, corrections, and debates layered on top of the structure. "This endpoint used to be deprecated, but ops re-enabled it for the migration," "Note: the sessions table doesn't actually enforce the FK in production," etc. These notes live in Slack today and disappear.

This ticket introduces a first-class annotations layer. It is not a chat product; it is a persistent notebook pinned to graph entities.

## Scope

- A comment panel attached to each node and link's detail view. Users can read existing annotations and add new ones.
- Annotations carry: target type (node or link), target ID, author, text, timestamp, and optionally a reply thread (one level deep).
- Server storage and API per GE-020.
- Author attribution via the chosen auth model (GE-020).
- A global "annotations" panel showing recent annotations across the whole graph (sortable by timestamp or author).
- Visual indicator on nodes / links that have annotations (a small badge, numeric count).
- Deletion: authors can delete their own annotations; admins (if the auth model supports roles) can delete any.

## Out of scope

- Real-time sync of annotations (that is GE-024). For MVP, the UI re-fetches on open or on a polling cadence.
- Rich text / markdown rendering. Plain text only for MVP.
- Attachments (images, files). Post-MVP.
- @mentions, notifications. Post-MVP.
- Moderation tools beyond own-delete / admin-delete.

## Acceptance criteria

- A user can add, view, and delete annotations on nodes and links.
- Annotations persist across sessions and are visible to other users with access.
- The visual indicator on annotated entities is correct and updates as annotations are added / deleted.
- Reply threads (one level) work.
- The global annotations panel shows recent activity.

## Risks

- Spam / abuse. Not MVP-scale concern but budget for it before a wider rollout.
- Annotation count visibility on large graphs can become visual noise — keep the badge subtle.
- The one-level reply constraint must be enforced in the data model, not just the UI.

## Notes for the implementer

This is plumbing plus a small UI. Keep the data model flat — a single `annotations` table with optional `parentId` for replies. Do not build a full comment-system abstraction.
