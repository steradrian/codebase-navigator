# GE-016 — Schema diff view

**Status:** DONE
**Phase:** Phase 2 — Intelligence
**Effort:** M
**Depends on:** GE-003, GE-010
**Blocks:** —

## Summary

Given two schema snapshots, compute and render a structural diff — added / removed / modified nodes, links, and paths — so users can see what changed between versions.

## Context

Systems evolve. Seeing "what's different since last week" is valuable for architecture reviews, release notes, and change management. The diff view is also a natural companion to any future versioning story — CI-driven re-imports (GE-025) need a way to surface what changed.

MVP scope is a client-side diff between two loaded schemas: the current working schema and a reference schema loaded from file. Full versioning and history are deferred.

## Scope

- A diff mode entered from the main UI. The user picks a reference schema (from a file upload or a prior export) — this is the "baseline."
- The current working schema is compared against the baseline. The diff computation is pure, testable, and produces a structured report:
  - Nodes: added, removed, modified (with per-field changes).
  - Links: added, removed, modified.
  - Paths: added, removed, modified (including changes to step sequences and annotations).
- Rendering modes:
  - **List view**: structured list of changes, groupable by type and navigable — clicking a change focuses the camera on the relevant node or link.
  - **Overlay view**: the graph itself is color-coded — green for added, red for removed, yellow for modified. Removed nodes render as ghosts (translucent); added nodes pulse subtly.
- Exit diff mode returns to normal view.

## Out of scope

- Three-way diff (comparing two baselines against a current). Two-way only.
- Semantic diff (understanding that renaming a node is not the same as delete + add). Structural diff only — rename is detected as a delete + add unless node IDs match.
- Merging (taking a diff and applying it selectively). That is the merge engine's (GE-007) concern, and it operates on candidate schemas, not diffs.
- Time-series history with multiple checkpoints. Two snapshots only.
- Persistence of diff baselines.

## Acceptance criteria

- Selecting a baseline file shows a complete list of changes against the current working schema.
- Every change type (add/remove/modify for nodes/links/paths) is represented and navigable.
- The overlay view correctly color-codes the graph.
- Modified fields are visible per-entity (e.g., "description changed from X to Y").
- Diff computation is pure and covered by unit tests for each change type.

## Risks

- Modification detection on paths is subtle — adding a step in the middle shifts subsequent step indices. Use step-level equality rather than index-level.
- Overlay view on a graph that also has blast radius or guided path active will conflict. Gate the modes — only one overlay at a time.
- Visual noise at high change counts. Paginate the change list.

## Notes for the implementer

The diff function is testable in isolation — start there. Once the computation is correct, the UI is straightforward. Do not let rendering polish delay shipping the computation and list view.
