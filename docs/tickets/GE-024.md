# GE-024 — Real-time sync (WebSockets)

**Status:** TODO
**Phase:** Phase 3 — Scale
**Effort:** L
**Depends on:** GE-020, GE-021, GE-023
**Blocks:** —

## Summary

Schema changes (node edits, path creation, annotations) made by one user propagate to all other connected viewers in near-real-time via WebSockets. Editing the graph becomes a collaborative experience.

## Context

Once graphs are server-stored and multiple people are viewing and annotating them, the absence of real-time sync becomes a usability problem: users look at stale views, conflicting edits clobber each other, and demos feel broken ("wait, refresh the page").

This ticket adds the real-time layer. Scope is bounded — MVP does not attempt operational transformation or Figma-style live cursors. Simple event broadcasting is enough.

## Scope

- A WebSocket channel per graph. Authenticated clients subscribe when they open the graph.
- The server broadcasts an event for every mutation: node created / updated / deleted, link created / updated / deleted, path created / updated / deleted, annotation created / deleted.
- Clients apply incoming events to their local state. Conflict handling: last-write-wins for simple field edits, with a prompt if the user is currently editing a field that was changed remotely.
- Presence: a lightweight indicator showing how many users are currently viewing the graph. Optional: their cursor positions or currently selected node.
- Disconnection handling: automatic reconnect with exponential backoff. On reconnect, the client re-syncs by fetching the current state.

## Out of scope

- Collaborative cursors / avatars. Optional stretch — nice demo but not load-bearing.
- Conflict-free replicated data types (CRDTs) or operational transformation. Simple last-write-wins is enough for MVP.
- Server-side change-log history for conflict review. Clients see the latest state; disputes are resolved via annotations.
- Offline mode with local queue and sync on reconnect. Post-MVP.
- Real-time sync for layout positions (where each user has the camera). URL state (GE-022) covers this asynchronously; live camera sync is a post-MVP flourish.

## Acceptance criteria

- Two browser tabs on the same graph see each other's edits within a second.
- Adding, editing, and deleting nodes / links / paths / annotations all sync correctly.
- Disconnecting one tab does not break the other; reconnecting brings the tab back into sync.
- Simultaneous conflicting edits do not crash the server or either client; the last write wins.
- The presence indicator correctly reflects active viewers.

## Risks

- WebSocket scaling — at multi-thousand-user scale, a single-process WS server dies. Not an MVP concern but flag for the infra roadmap.
- Event ordering. The broadcast must preserve the server's write order, or clients diverge.
- Reconnect storms. Exponential backoff with jitter prevents them.
- Security — the subscription auth must be re-verified; a client cannot subscribe to a graph it does not have read access to.

## Notes for the implementer

Keep the event schema narrow — one message type per mutation type, with the entity ID and the new value. Do not build a generic pub/sub framework. The messages are the contract; keep them boring.
