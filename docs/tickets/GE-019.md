# GE-019 — Instanced rendering + LOD

**Status:** PARTIAL — LOD label culling landed; instanced rendering deferred (see resolution notes)
**Phase:** Phase 3 — Scale
<br>**Effort:** M
**Depends on:** GE-001
**Blocks:** —

## Summary

Replace per-node `THREE.Mesh` allocations with `THREE.InstancedMesh` so thousands of nodes render in a single draw call. Introduce level-of-detail rules for nodes, labels, and links so distant geometry degrades gracefully instead of crashing the GPU.

## Context

Today, each node is its own `THREE.Mesh` with its own material, and each label is a sprite with a one-shot canvas texture. At ~1,000 nodes, draw-call overhead dominates frame time and the browser tab slows visibly. Label textures also leak — they are created per node and never pooled.

`InstancedMesh` solves draw calls: one geometry, one material, thousands of instance transforms. Level-of-detail (LOD) rules solve rendering cost: geometry degrades as the camera pulls back.

## Scope

- Replace node meshes with `THREE.InstancedMesh`. Per-instance attributes for position, scale, and color. Selection and highlighting update instance attributes rather than swapping meshes.
- Replace link lines with an efficient batched representation — either a single `LineSegments` with all endpoints in one buffer, or custom shader-based rendering. Whichever is simpler and measurably faster at 1,000+ links.
- Introduce LOD rules based on camera distance:
  - **Close**: full sphere geometry, glow halo, full label text, all link detail.
  - **Medium**: simplified sphere (low-poly), no glow, abbreviated or hidden labels, links still rendered.
  - **Far**: point-sprite nodes (single-pixel-ish), no labels, cluster-level aggregate links only.
- Label sprite pool: fixed-size array recycled based on which nodes are closest to the camera. Only visible labels are mounted.
- Selection, guided path highlighting, and blast radius all continue to work correctly — the per-instance color attribute is the mechanism.

## Out of scope

- Replacing Three.js with a lower-level renderer (regl, raw WebGL, WebGPU). Keep Three.js.
- Custom shaders beyond what is required for the instanced render path.
- Texture atlasing for labels. Nice-to-have, not MVP.
- Post-processing effects (bloom, SSAO). Post-MVP.

## Acceptance criteria

- At 1,000 nodes, framerate is stable at 60fps when the simulation is idle.
- At 2,000 nodes, framerate remains interactive.
- LOD transitions are not visually jarring — tune thresholds and transition speeds.
- Selection, highlighting, and guided path visuals work identically to the pre-instanced version at small scale.
- No label texture leaks — verifiable via repeated schema reload cycles showing stable GPU memory.

## Risks

- `InstancedMesh` requires per-instance color updates via an `InstancedBufferAttribute`. The update cadence must be throttled — uploading every frame when only a handful of nodes changed is wasteful.
- LOD threshold tuning is sensitive. Shipping with wrong thresholds means users see a stuttering transition every time they zoom. Prototype with a real large graph.
- Sprite pooling must respect z-ordering — labels in the background should not occlude foreground ones.

## Notes for the implementer

Profile before and after on a synthetic large graph. If the feature does not demonstrably move the needle on framerate at 1,000+ nodes, something is wrong. Use the browser's performance tools — do not ship based on vibes.

## Resolution notes

**Shipped**: Camera-distance LOD for labels. Labels fade linearly between 250 and 450 units from the camera; beyond that they hide entirely. "Interesting" nodes (selected, on-path, impacted by blast, changed in diff, collapsed cluster parents) are exempted from fading so they remain readable at any zoom level. Cheap, visible even at small graphs (cleaner zoom-out view), no refactor risk.

**Deferred as follow-up (GE-019b)**: `THREE.InstancedMesh` migration for nodes, batched line geometry for links, and point-sprite LOD for distant nodes. Rationale: `InstancedMesh` doesn't support per-instance opacity with the built-in materials — every visual mode the app now has (selection dim, path dim, blast severity gradient, diff overlay, collapsed-cluster pulse) relies on `material.opacity` mutation. A custom shader per-instance-color-and-opacity is a meaningful engineering investment, and the current per-mesh approach is fine up to several hundred nodes. File when a workload actually hits 500+ nodes and perf profiling shows draw-call overhead dominating.

**Not shipped**: Point-sprite LOD, texture atlasing for labels, sprite pooling. All tied to the instanced-rendering refactor.
