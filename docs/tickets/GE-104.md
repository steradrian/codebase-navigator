# GE-104 — Filter rail

**Status:** DONE
**Phase:** UX / Visualization
**Effort:** M
**Depends on:** GE-103 (entity facet)
**Blocks:** —

## Summary

A left-side collapsible sidebar with multi-select filters across type, entity, and origin. Active filters dim non-matching nodes (and their connecting edges), letting users narrow to arbitrary subsets of the graph.

## Context

Today the only way to narrow the graph is search (by name) or mode-specific dimming (selection, path, blast). None of those expose the structural facets. A filter rail is the primary "look only at this slice" mechanism.

Combined with entity tagging (GE-103), filters turn the graph from a read-only artifact into an explorable one: "show me just Payment + API + auto:openapi" narrows to the backend surface of one entity. "Show me codebase UI files tagged Bonus" narrows to the hook/component side.

## Scope

- Collapsible sidebar on the LEFT of the canvas. Width ~240px when expanded, ~36px icon-only when collapsed. Toggle chevron at top.
- Three facet groups (GE-108 will add a bridge from the legend to this):
  1. **Type** — every key in `schema.nodeTypes`, with count badges.
  2. **Entity** — every entry in `schema.meta.entities` (plus a special "Unclassified" for nodes without entity), with count badges.
  3. **Origin** — the three origins that exist in the schema, with counts.
- Each group has a master checkbox (toggle all in this group) and per-item checkboxes.
- "Clear filters" button at the bottom of the rail.
- Active filters are AND-across-groups, OR-within-a-group. (Show me `(ui OR api) AND (payment) AND (auto:openapi OR manual)`.)
- When ANY filter is active, the animation loop dims all non-matching nodes to ~8% opacity and their edges to ~2% opacity. Matching nodes render at full brightness regardless of other modes except:
  - Selection still takes precedence (the selected node + its connections stay visually prominent within the filtered set)
  - Path / blast / diff modes stack — filters apply first, the mode's styling applies within the filter subset
- Filter state lives in component state, synced to URL state (GE-022) so shared links preserve the filter.
- Active filter count shows as a small badge on the rail's collapsed icon.

## Out of scope

- Free-text filter by node name / description. Search already covers this.
- Regex or advanced filter expressions. If users want boolean logic beyond AND/OR, defer.
- Saving filter presets (e.g. "Payment Backend" as a named filter). Future ticket if requested.

## Acceptance criteria

- Opening the rail shows all three groups with accurate counts.
- Selecting one type (e.g. "api") immediately dims everything non-api.
- Selecting two types is an OR — both appear.
- Selecting one type AND one entity narrows to the intersection.
- "Clear filters" resets to all-on in every group.
- Collapsing the rail persists the filter state and shows the active-count badge.
- URL round-trips: copy-link with filters active lands a new tab on the same filtered view.
- Combines correctly with blast radius: if a blast emanates from a filtered-out node, the radius still renders over the filtered subset.

## Risks

- Interaction layering with blast / diff / path modes will take tuning. Keep the animation-loop logic readable — filters are always the outermost "is this node considered" check; modes style within the filtered set.
- Count recomputation on every filter change is cheap but should be memoized against the schema, not re-run per render.
- Entity counts need to include "Unclassified" — nodes with `entity === undefined` — which is a bucket, not a value.

## Notes for the implementer

Store filter state as `{ types: Set<string>, entities: Set<string>, origins: Set<string> }` where an empty Set means "all allowed" for that group. A populated set means "only these allowed." That's simpler to reason about than allow/deny lists.

The animation loop gains a `isFilteredIn(node)` helper that's checked once per node per frame. Cheap.
