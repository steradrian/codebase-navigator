# GE-001 — TypeScript migration

**Status:** DONE
**Phase:** Scaffolding
**Effort:** M
**Depends on:** —
**Blocks:** GE-002, GE-003, and every ticket after

## Summary

Migrate the existing JavaScript codebase to TypeScript with a loose initial configuration, then tighten progressively as subsequent tickets land.

## Context

The project is currently ~1,056 lines of vanilla JavaScript across four files. The data model is about to grow significantly (link types, node metadata, parent/child hierarchy, annotations, origin tracking) and several new systems are about to be added (OpenAPI importer, merge engine, path authoring). Every untyped module written from this point forward will cost more to retrofit later.

This is the last inexpensive moment to add TypeScript. Moving now means every subsequent ticket can be built type-safe from day one, catching schema shape errors at compile time rather than in the renderer.

## Scope

- Add TypeScript as a devDependency and configure a `tsconfig.json` tuned for gradual migration. Start permissive: `strict: false`, `noImplicitAny: false`, `allowJs: true`. These settings will tighten as the code stabilizes.
- Configure Vite so `.ts`, `.tsx`, `.js`, and `.jsx` coexist during the migration.
- Translate the four existing source files to TypeScript, preserving exact runtime behavior.
- Define interim type definitions for the current schema shape (`NodeType`, `Node`, `Link`, `Path`, `PathStep`). These types are temporary scaffolding — they will be fully revised in GE-003.
- Add a `@/` path alias resolving to `src/` in both `tsconfig.json` and the Vite config. Update all existing imports to use it where natural.
- Confirm the app builds, runs, and behaves identically post-migration.

## Out of scope

- Enabling `strict: true` or `noImplicitAny: true` — tighten in a follow-up once the new data model (GE-003) is in.
- Revising the schema shape — that is GE-003's job, not this ticket's.
- Refactoring component structure, extracting hooks, or splitting `GraphExplorer.tsx`.
- Any cosmetic changes.

## Acceptance criteria

- `npm run dev` produces a working app with zero visible regressions.
- `npm run build` succeeds and produces a working bundle.
- `tsc --noEmit` passes.
- All four source files live at `src/*.ts` or `src/*.tsx`.
- The `@/` alias works in editor (IntelliSense) and at build time.
- Existing JSDoc annotations on `ForceSim3D` have been converted to TypeScript types, not discarded.

## Risks

- `@types/three` must match the exact version of the `three` dependency or types drift in confusing ways.
- React 18 + StrictMode + TypeScript may surface previously-silent type issues in effect cleanup functions. Fix at the source; do not suppress with `any`.
- The `ForceSim3D.tick()` inner loops mutate node objects — the type for a simulated node must be a superset of the input node, carrying `x/y/z/vx/vy/vz`. Model this cleanly (e.g., `SimulatedNode extends Node`).

## Notes for the implementer

Keep this migration mechanical. Do not take the opportunity to refactor, rename, or restructure — every unrelated change makes the diff harder to review and raises the chance of introducing a runtime regression. If something looks wrong, open a follow-up ticket rather than fixing in place. The goal is a boring, reviewable diff that unblocks every ticket after this one.
