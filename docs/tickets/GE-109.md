# GE-109 — BE codebase parser (Go-first, plugin architecture)

**Status:** DONE (pure-parser portion; UI dialog integration lands in the codebase-import-dialog work)
**Phase:** Ecosystem / Full-stack parsing
**Effort:** L
**Depends on:** GE-103 (entity tagging), GE-003 (schema)
**Blocks:** GE-110

## Summary

Extend the codebase parser to extract backend source — starting with Go, with a plugin architecture designed for adding Node/Python/Rust later. Emits API nodes for each HTTP handler, database nodes for struct declarations, and dependency edges between files. Every emitted entity carries `origin: auto:codebase` with a language suffix for detection.

## Context

The frontend codebase parser (GE-026) covers the client side and is linked to OpenAPI via GE-026c. The backend is the missing third of the full-stack flow. Without a BE parser, the admin-dashboard demo stops at the API boundary — users see what calls an endpoint but not what implements it.

Go is the primary target (the user's admin-api is Go). But committing to a single language would be short-sighted — the parser should be structured from day one so adding another language is "drop in a module," not "rewrite the pipeline."

## Scope

### Language-plugin architecture

- New directory `src/importers/codebase/backends/` with:
  - `index.ts` — language-dispatch entry. Picks a plugin based on file-extension majority.
  - `types.ts` — shared `BackendPlugin` interface: `{ language: string, fileExtensions: string[], extract(files, context): BackendResult }`.
  - `go.ts` — full Go implementation.
  - `nodejs.ts`, `python.ts`, `rust.ts` — stubs that declare fileExtensions and a placeholder `extract` returning empty — just enough to be picked up when the user picks a non-Go folder, and to ship a "Not yet supported" warning gracefully.
- The frontend parser (`parseCodebase` in `src/importers/codebase/index.ts`) gets a new mode flag: `{ backend: boolean }`. When true, it dispatches to `backends/index.ts` instead of running the Next.js FE heuristics.
- Import UI gets a radio: "Is this a frontend or backend codebase?" Defaults to FE.

### Go extractor (the real work)

- Recognize common router registrations across idiomatic Go:
  - `net/http`: `http.HandleFunc("/path", handler)` / `mux.HandleFunc(...)`
  - `gorilla/mux`: `r.HandleFunc("/path", handler).Methods("GET")`
  - `chi`: `r.Get("/path", handler)` / `r.Post(...)` / etc.
  - `gin`: `r.GET("/path", handler)` / `g.POST(...)` etc.
  - `echo`: `e.GET(...)` / `e.POST(...)`
  - Kong-style handlers: function signatures matching `func(c Context) error` patterns
- For each detected handler registration, emit an **api-type node** with:
  - `id: codebase:go:handler:<method>:<sanitized-path>`
  - `name: "<METHOD> <path>"` (matches OpenAPI node name format — critical for GE-110 linking)
  - `type: 'api'`
  - `origin: 'auto:codebase'`
  - `description`: the file + line where the handler is registered
  - `metadata.backend: 'go'` — distinguishes from the FE side
- Extract `type X struct { ... }` declarations as **database-type nodes** (they're the domain entities on the backend):
  - `id: codebase:go:struct:<packagepath>.<StructName>`
  - `name: StructName`
  - `type: 'database'`
  - `origin: 'auto:codebase'`
- Parse `import` blocks for intra-module dependency edges, same pattern as the FE parser.

### Entity tagging

- Use GE-103's entity extractor on all emitted nodes. For Go, the most useful signals are: package name, file path (`admin/handlers/payments/...` → `payment`), struct name.

### File + path filtering

Go-specific ignores in addition to the shared `SKIP_PATH_PATTERNS`:
- `vendor/` directories
- `_test.go` files
- Generated files with `// Code generated by` header

### UI

- The existing `CodebaseImportDialog` gains a radio at the top: "Frontend" / "Backend". Defaults to "Frontend" (preserves current behavior).
- When "Backend" is selected, file-reading uses a Go-aware extension filter (`.go` + a couple of config file types).
- Preview shows per-handler + per-struct counts separately.

## Out of scope

- gRPC handler extraction. REST only for MVP.
- Middleware / interceptor modeling. Handlers only.
- Database query extraction (SQL inspection). Struct-declarations-as-schemas is the approximation.
- Interface/abstract-method resolution. If a handler is registered via interface indirection, we'll miss it. Accepted loss.
- Package graph for cross-package dependencies beyond file imports.

## Acceptance criteria

- Running the Go backend parser on a realistic Gin / chi / gorilla codebase emits at least 80% of the real handler registrations as api nodes.
- Struct declarations in public packages are emitted as database nodes with the correct name.
- Entity tagging populates on both handler and struct nodes via the GE-103 heuristics.
- Stub language plugins (nodejs / python / rust) correctly advertise their extensions and surface a clear "Not yet supported — language: X" warning when picked.
- The FE codebase parser's behavior is unchanged when `backend: false`.
- The import dialog's radio toggle controls the dispatch.
- `tsc --noEmit`, `npm test`, `npm run build` all pass. New unit tests cover at least: Gin route registration, chi route registration, struct declarations, file-import resolution.

## Risks

- **Regex across Go is trickier than across JS.** Multi-line function definitions, struct embedding, method receivers. Start with the tightest pattern and widen only as needed.
- **Generated code pollution.** A single forgotten filter for `// Code generated by protoc` emits hundreds of junk nodes. Be aggressive on generated-file detection.
- **Route registration via helpers.** Some codebases do `RegisterAdminRoutes(r)` then define handlers inside. One level of indirection is probably fine to follow (analog of GE-026c's pass 3); deeper indirection isn't tractable without an AST.

## Notes for the implementer

Use the same regex-first approach as the FE parser — it's honest about what it's doing, zero dep, tight bundle. When regex can't handle something, note it in a warning and skip rather than trying to add AST machinery mid-ticket.

Plugin structure makes adding other languages a focused exercise. Document the plugin interface clearly in `types.ts`.

For the `CodebaseImportDialog` changes, consider extracting the file-read + preview flow into a reusable hook since both FE and BE modes share ~80% of the UI.
