# GE-105 — Connection panel redesign

**Status:** DONE
**Phase:** UX
**Effort:** M
**Depends on:** —
**Blocks:** —

## Summary

Restructure the side panel's connection list so adjacent nodes communicate — at-a-glance — what they ARE and how they relate. Sections by semantic category, per-type icons, cleaner typography, and a breadcrumb strip pulling in GE-101's history.

## Context

From live user feedback looking at a selected node (`tags`): each row in the connection list currently shows raw `IN/OUT` direction + a type tag like `Dependency` + the raw source/target path. Users have to mentally combine multiple pieces of data to understand what the row tells them. With dense graphs (admin-dashboard) this cognitive tax compounds.

The fix isn't more data — it's better shape. Group connections by what the relationship MEANS, not by direction.

## Scope

### Section-based layout

The connection list becomes category-grouped. Each section has a header with the count and an icon:

| Section | Includes | Visual |
|---|---|---|
| **Imported by** | incoming dependency links | 📄 icon, cyan accent |
| **Imports** | outgoing dependency links | 📄 icon, cyan accent |
| **API calls out** | outgoing data_flow links where target is api type | 🌐 icon, green accent |
| **Called by** | incoming data_flow links where source is codebase type | 📄 icon, green accent |
| **Reads / writes** | data_flow links to database nodes | 🗄 icon, blue accent |
| **Triggers / triggered by** | triggers-type links in either direction | ⚡ icon, yellow accent |
| **Appears in paths** | existing "Related paths" section | ◈ icon, path color |
| **Annotations** | existing annotation panel | 💬 icon, purple accent |

Empty sections are omitted (no "Imports (0)" noise).

### Row shape

Each row becomes two lines:
- **Line 1**: icon + node name + type badge (color dot + short label)
- **Line 2**: the relationship's SHORT description — what the link actually encodes ("imports via `fetchTags`", "calls with body `{ status }`")

Drop the redundant `source → target` path text from rows — it's encoded in the section header.

### Breadcrumb strip

Above the node title, render the GE-101 history breadcrumb as a compact pill row. Clickable chips. Appears only when history has at least 2 entries.

### Entity chip

If the selected node has an `entity` field (post GE-103), show it as a pill next to the type badge. Colored per the entity's palette hash.

## Out of scope

- Grouping connections BY the peer node (e.g. "these 3 edges all touch the same node, collapse them"). Post-MVP.
- Showing only a subset of connections with a "show more" link at high counts. Current list is already scrollable.
- Inline expand/collapse of a row to see the full link description.

## Acceptance criteria

- Selecting a node with mixed connection types shows the sections above, each with accurate counts.
- Rows are visually scannable — name + type + one line of relationship context, no more.
- Empty sections don't render.
- The breadcrumb strip appears when ≥2 selections in history.
- Entity chip appears when the selected node has entity set.
- All existing interactions (click to navigate to peer) still work.

## Risks

- The redesign affects the MOST frequently-used UI surface — regression risk on annotations, blast radius panel, path step panel. All of those share the same side-panel container. The ticket is scoped to the INFO mode only; annotations and paths keep their existing look.
- Icons risk looking inconsistent with the existing aesthetic (which is mostly typography + subtle color). Use Unicode characters rather than an icon library to stay bundle-tight.

## Notes for the implementer

The current INFO MODE JSX is a big inline blob. Extracting sub-components here (e.g. `ConnectionSection`, `ConnectionRow`) is worth it even if the ticket is scoped to INFO mode — makes the redesign readable and avoids duplication between GE-105 and GE-109/110 which will also surface similar data.

Consider extracting a pure helper `groupConnections(connections, schema): Section[]` so the categorization logic is testable independently of the render.
