# GE-110 — BE handlers → OpenAPI operations linker

**Status:** DONE
**Phase:** Ecosystem / Full-stack parsing
**Effort:** M
**Depends on:** GE-109 (BE codebase parser), GE-006 (OpenAPI parser), GE-026c (existing FE linker — same pattern)
**Blocks:** —

## Summary

Extend the existing code ↔ API linker (GE-026c) to also match backend handlers to OpenAPI operations. When both a Go handler for `GET /admin/players` and an OpenAPI operation `GET /admin/players` exist in the graph, emit an edge showing that the handler IMPLEMENTS the operation. Closes the full-stack flow: UI calls API spec, API spec is implemented by BE handler.

## Context

GE-109 emits Go handler nodes with names in the exact same `METHOD /path` format that the OpenAPI parser uses. This alignment makes the linking trivial — byte-equal name matching is enough. The existing FE linker (GE-026c) already demonstrates the pattern.

## Scope

- Extend `extractCodebaseApiLinks` (or spawn a sibling `extractBackendApiLinks` if coupling gets awkward) to scan for BE handler nodes:
  - Select nodes where `origin === 'auto:codebase'` AND `metadata.backend === 'go'` (or other BE language markers).
- For each BE handler node, find the matching OpenAPI operation by equal `name` field.
- If a match is found, emit an edge:
  - `source: <openapi op node id>`
  - `target: <be handler node id>`
  - `label: 'implemented by'`
  - `type: 'data_flow'` (same type family as the FE linker's edges)
  - `origin: 'auto:codebase'`
  - Deterministic id via existing `linkId()`
- If the OpenAPI spec has a handler BE-side but no spec-side counterpart (or vice versa), surface as `unmatched_backend_handler` / `unmatched_openapi_operation` warnings.
- UI: the existing "↔ Link imports" dialog gains coverage — same button, same dialog, the linker now runs both FE and BE passes. No new button needed.

## Out of scope

- AST-based match refinement (e.g. argument type comparison). Path + method equality is sufficient for MVP.
- Cross-microservice routing (when a single spec covers multiple BE services). Single-repo assumption.
- Automatic detection of spec drift (BE has `/foo`, spec has `/bar`). Warnings surface divergence; fixing is the user's job.

## Acceptance criteria

- Running the link dialog on a graph with an OpenAPI-imported spec + a Go BE codebase produces `implemented by` edges for every path-and-method that appears in both.
- Warnings list any unmatched BE handlers AND unmatched OpenAPI ops so users see both sides of a drift.
- Rerunning is idempotent (existing edges dedup'd by ID).
- Existing FE linker behavior unchanged — this is additive.

## Risks

- Path format mismatches between BE frameworks and OpenAPI specs. Example: Gin uses `:id`, OpenAPI uses `{id}`. The BE extractor should normalize to OpenAPI format at emit time (so the linker never sees the mismatch). GE-109 must handle this — document clearly.
- Some BE routes are registered without a method constraint (e.g. `http.HandleFunc` serves all methods). The BE extractor should emit one handler per (method, path) or explicitly emit `ANY` and the linker skips those.

## Notes for the implementer

Given GE-026c already has well-factored extraction + linking code, extending it is mostly configuration: add a BE node selector, loop over matches, emit edges. Keep the three-pass structure of GE-026c intact — BE matching is effectively a "pass 4" that operates on a different node set.

The warnings UI in `LinkImportsDialog` needs a small tweak to show which side of the stack a warning came from (FE / BE). Trivial once the warning struct grows an `origin` field.
