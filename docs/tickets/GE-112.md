# GE-112 — Hub visual marker

**Status:** TODO
**Phase:** UX / Visualization
**Effort:** S
**Depends on:** GE-115b (provides `node.isHub` via entity propagation)
**Blocks:** —

> **Amendment (post two-level catalog decision)**: GE-115b now computes `node.isHub` based on entity-span (≥ 3 distinct entities reaching a node via propagation). This ticket's scope updates accordingly: consume `node.isHub` from the schema instead of re-deriving hubs from degree at render time. The visual spec below is unchanged; only the detection source changes.

## Summary

Nodes whose degree is in the top 5% of the graph render with a visible outline ring — a "this is infrastructure, not a leaf" marker. Users learn to recognize hubs before clicking them.

## Context

In `Ann test` the top 5% (degree ≥20) is 29 nodes — all infrastructure files (utils, index, openapi-client, pagination, currency). They look identical to a leaf component until you select them and the connection list explodes. A subtle visual cue up front sets expectations and makes it obvious which nodes to avoid entering "info overload" via accidentally.

## Scope

- Compute a per-schema degree distribution, memoized on `schema.nodes.length + schema.links.length`.
- Threshold: p95 by default. Flag nodes at or above the threshold as hubs.
- Hub nodes render with an additional ring/halo — a thin outline in a neutral bright color (white at ~40% opacity or similar), slightly larger than the node sphere. In 2D mode, a ring around the circle.
- Hub marker renders regardless of color mode (type / entity).
- Hub marker dims with the same rules as the node it belongs to (filter, selection, path, blast).
- Hover tooltip (from GE-102) on a hub mentions degree: `utils · ui · 76 connections`.
- No change to the legend; no new toggle. The marker is ambient.

## Out of scope

- User-configurable threshold. p95 is the default; if it becomes an issue we add a slider later.
- Different marker styles for mega-hubs (deg >50) vs regular hubs. One style only.
- Changing force-simulation behavior for hubs (e.g. heavier mass). Physics stays as-is.

## Acceptance criteria

- On `Ann test`, ~29 nodes render with the hub ring. Top hub (utils, 76) is clearly marked.
- On a small graph (<40 nodes, uniform degree), few or zero nodes get the marker — the p95 threshold produces nothing meaningful below a certain size. That's fine.
- Toggling filters, selection, and path modes does not break the hub ring rendering.
- Tooltip on a hub includes degree.

## Risks

- Visual noise if p95 happens to flag too many small hubs on a dense graph. If tuning is needed, raise to p97 or set a minimum absolute degree (e.g. `max(p95, 15)`). Keep the tunable as a single constant in the module.
- InstancedMesh (GE-019b, deferred) — when that lands, hub rings need to batch too. For now they can be individual meshes since hubs are a small fraction.

## Notes for the implementer

Degree computation is already happening somewhere in the force sim / connection panel — reuse if possible, otherwise a single `Map<nodeId, number>` pass over `schema.links` memoized against the schema. Render the ring as a child mesh of the node group so it inherits position/dim transforms.
