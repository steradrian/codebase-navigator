# GE-103 — Entity tagging (schema v1.1)

**Status:** DONE
**Phase:** Data model / Intelligence
**Effort:** M
**Depends on:** GE-003 (schema v1.0)
**Blocks:** GE-104, GE-106, GE-109, GE-110 (and indirectly GE-102, GE-105 — they show entity if present)

## Summary

Add a first-class `entity` field to the v1.0 schema, bump to **v1.1**, and auto-populate it via heuristic extractors that run on every import. Users review the discovered entity set after import. The entity field is the spine for every subsequent "show me the Payment flow"-style feature (filter, color-by-entity, BE linker).

## Context

The graph today describes WHAT each node is (type: ui / api / database / …) but not WHAT IT'S ABOUT. In a real admin system every meaningful node is a member of a domain entity — Customer, Payment, Bonus, Document, Session — and users want to reason along that axis. Without it, the graph is a nice technical diagram but can't tell the domain story.

Entity should be a first-class field (not buried in `metadata`) because every downstream feature queries against it. A schema-version bump is cheap.

## Scope

### 1. Schema v1.1

- Add `entity?: string` on `Node` (optional — not all nodes map cleanly to an entity).
- Bump `SCHEMA_VERSION` constant to `'1.1'`.
- Add a v1.0 → v1.1 migration step that tries to infer `entity` for existing nodes using the same heuristics as fresh imports.
- The validator doesn't reject missing `entity` — it's optional. It only validates that if present, it's a non-empty string.

### 2. Heuristic entity extractor

A pure function `extractEntity(node, context): string | undefined` that runs on every emitted / edited node. Extractors priority-order:

| Priority | Source | Signal |
|---|---|---|
| 1 | Explicit override (`manualOverrides.includes('entity')`) | skip extraction |
| 2 | OpenAPI node tags | first tag (`tags: [Customer]` → `customer`) |
| 3 | OpenAPI schema name | strip `Admin`, pluralize→singular (`AdminPayments` → `payment`) |
| 4 | OpenAPI path | first meaningful segment (`/admin/payments/...` → `payment`) |
| 5 | Codebase file path | known domain folder (`modules/payments/...` / `lib/api/bonuses/...`) |
| 6 | Codebase file name | suffix / prefix (`use-all-payments.ts` → `payment`) |
| — | fallback | undefined — user sets manually |

All extractors normalize to lowercase singular via a small `singularize()` helper (`customers` → `customer`, `bonuses` → `bonus`, `freespins` → `freespin`).

### 3. Entity dictionary + review banner

- On every import (OpenAPI, codebase, codebase linker), the extractor runs against the result.
- Post-import, the UI surfaces a **review banner**: "7 entities discovered: customer, payment, bonus, document, rakeback, freespin, account. Review."
- Clicking "Review" opens a modal listing the discovered entities, how many nodes each tags, and a "merge" control to consolidate variants (e.g. user wants to merge `player` into `customer`).
- The merged dictionary is stored on `schema.meta.entities: string[]` — the canonical list. Extractors prefer to match into this list when it exists.

### 4. Editor override

- The node editor (GE-009) gets a new Entity field: a text input with autocomplete against `schema.meta.entities`.
- Editing `entity` on an auto-generated node marks it as a manual override via the existing `manualOverrides` tracking.

## Out of scope

- Automatic dictionary curation beyond what the user approves in the review step.
- Entity-to-entity relationships (e.g. "Payment belongs to Customer"). Future ticket if useful.
- ML-based entity extraction. The heuristics are enough for the domain-well-organized codebases we care about.

## Acceptance criteria

- Post-migration, the demo schema has populated `entity` fields on at least 80% of its non-domain nodes.
- Running `extractEntity` on the imported OpenAPI spec populates `entity` on every api and database node where either a tag or path gives a signal.
- Running on a realistic codebase sample (`admin-dashboard`) populates `entity` on every file under `modules/`, `lib/api/`, `hooks/` folders.
- Post-import review banner fires with the full list of discovered entities.
- The review modal's "merge X into Y" action reassigns every node from X to Y in one atomic schema update.
- Manual override persists across re-imports (via existing `manualOverrides` mechanism).
- Validator accepts the new `entity` field; rejects empty-string entity values as invalid.

## Risks

- **Heuristics fire in the wrong order or misclassify edge cases.** Solution: the review banner is the safety net. Users can correct errors in bulk via the merge control.
- **Plural vs singular normalization** has language-specific edge cases (`sessions` → `session`, but `analytics` shouldn't become `analytic`). Ship a small hard-coded exception list for these.
- **Migration of existing schemas** must be non-destructive. The migration step runs `extractEntity` on every node but only writes if the node doesn't already have `entity` set.

## Notes for the implementer

Put extractors in `src/schema/entity/extractor.ts` with individual pure functions for each source (openAPI tag / openAPI path / codebase path / etc.). Export a single `extractEntity(node, context)` that runs them in priority order.

For the review UI, reuse the modal styling from `ImportDialog`. Don't overbuild — a simple list + "rename" + "merge" is enough.

When bumping to v1.1, also update `LegacySchema` type if needed and the demo `schema.ts` pipeline.
