# GE-025 — CI/CD integration

**Status:** TODO
**Phase:** Phase 4 — Ecosystem
**Effort:** L
**Depends on:** GE-006, GE-007, GE-020
**Blocks:** —

## Summary

Automate graph regeneration on every deploy. The CI pipeline runs the importer (OpenAPI and / or codebase parser) against the latest source, merges the result via GE-007, and posts the updated graph back to the server.

## Context

Graphs drift. A static schema drifts silently the moment code changes. Manual re-imports work but require discipline. CI integration closes the loop — every push to main updates the canonical graph.

This ticket assumes the import pipeline (GE-006 OpenAPI, or later GE-026 codebase) and the server storage (GE-020) are already in place. It is the automation layer that binds them.

## Scope

- A CLI entry point that runs the importer against a configured input (a URL to an OpenAPI spec, a path to a codebase, etc.), merges the result with the current server-stored schema via GE-007's logic, and posts the merged schema back via the server API (GE-020).
- Configuration via a file (`graph-explorer.config.json` or similar) checked into the target repo, specifying sources, target graph ID, merge behavior, and authentication.
- GitHub Actions / GitLab CI / generic script examples in the docs so teams can wire it up quickly.
- A notification hook when the import surfaces conflicts — post to Slack / email / GitHub comment so humans know to review.
- An optional dry-run mode that reports what would change without writing.

## Out of scope

- A hosted CI service. Teams wire this into their own pipelines.
- Multi-source aggregation (pulling from OpenAPI + codebase + Figma in one run). Single source per run; compose at the team's discretion.
- Git-style commit history of graph changes. Post-MVP.
- Automatic resolution of conflicts. Conflicts are surfaced; humans resolve via the app.

## Acceptance criteria

- Running the CLI against a real OpenAPI URL and configured target graph produces an updated server-stored graph.
- Re-running the CLI without code changes is a no-op (determinism).
- Running against a deliberately conflicting change surfaces the conflict through the notification hook, does not silently overwrite, and posts a link to the in-app conflict review UI.
- Dry-run mode reports the diff without writing.
- Example pipeline configurations are documented for at least one CI provider.

## Risks

- Credentials handling. The CLI needs write access to the server. Use OIDC or short-lived tokens where possible; avoid long-lived secrets in repos.
- Pipeline run time. Large specs + large graphs can be slow. Profile and cache aggressively.
- Notification fatigue. Users stop reading alerts that fire too often. Only notify on conflicts, not on every successful merge.

## Notes for the implementer

This ticket depends on the server being ready and the import pipeline being stable. Do not start until both are in production use. When scoping, consider whether to distribute the CLI as a standalone npm package (broader adoption) or keep it in-repo (simpler initial implementation).
