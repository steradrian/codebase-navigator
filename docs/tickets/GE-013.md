# GE-013 — Semantic zoom with cluster collapse

**Status:** DONE
**Phase:** Phase 2 — Intelligence
**Effort:** L
**Depends on:** GE-003, GE-011
**Blocks:** GE-021 (lazy loading uses the same hierarchy)

## Summary

A hierarchical zoom model where, at high-altitude camera distances, the graph shows only top-level clusters (domains). Zooming in expands the hovered or selected cluster, revealing its children with animated transitions. At maximum zoom-out, 10,000 nodes become comprehensible; at maximum zoom-in, individual node detail is visible.

## Context

This is the single most important feature for making large graphs usable. Without semantic zoom, the tool can render 500 nodes and the user sees a hairball. With it, the tool can render 10,000 nodes and the user sees 8 clusters, drills into the relevant one, and finds the node they need.

It is also the single hardest feature in this phase. Correctness, performance, and UX must all land together — a half-implemented version is worse than nothing, because users will lose trust in which level of detail they are looking at.

## Scope

- Schema already supports `parent` / `children` and a `collapsed` boolean (GE-003). This ticket uses those fields to drive rendering.
- At high camera distance, collapsed parent nodes render as large, pulsing spheres labeled with the group name and a child-count badge. Child nodes are hidden; their links are aggregated into edges between parent clusters.
- Aggregated cluster-to-cluster edges carry a tooltip summarizing the underlying link count and dominant types ("12 connections: 8 data flow, 4 dependency").
- Hovering a collapsed cluster at medium distance expands it — children animate outward from the parent's position into their force-simulated positions, parent node fades out, individual links fade in.
- Zooming past a distance threshold auto-expands whatever cluster the camera is pointed at. Zooming out collapses clusters that fall outside the focus area.
- Manual override: users can click a cluster to pin it expanded (or collapsed) regardless of camera distance.
- Selection and guided paths work across the hierarchy. If a path step references a node inside a currently collapsed cluster, that cluster auto-expands for the duration of the path.

Three camera zones define behavior (tune thresholds during implementation):

| Zone | Camera distance | Default behavior |
|---|---|---|
| Far | > 400 units | All clusters collapsed |
| Medium | 150–400 units | Hovered / selected cluster expanded, others collapsed |
| Close | < 150 units | All visible clusters expanded |

## Out of scope

- More than two hierarchy levels. MVP supports domain → node; nested hierarchies (domain → service → endpoint) are post-MVP.
- User-authored hierarchies. Hierarchy comes from the schema's `parent` / `children` fields; authoring them is GE-009 or GE-025/026's concern.
- Automatic hierarchy inference (machine-proposed groupings). Post-MVP.
- Server-side aggregation of cluster edges — MVP computes aggregates client-side.

## Acceptance criteria

- On load with a schema containing at least two levels of hierarchy, the initial view shows only top-level clusters.
- Zooming in and hovering a cluster expands it with a smooth animation.
- Zooming out collapses clusters appropriately.
- Users can pin a cluster open or closed and the pin persists while zoom changes.
- Aggregate edges between clusters correctly reflect the underlying links.
- Guided paths auto-expand clusters as needed to keep the current step visible.
- Selection state is preserved across expand/collapse transitions.
- Performance is acceptable with ~500 nodes and 5–10 top-level clusters.

## Risks

- Force simulation interacts poorly with nodes appearing and disappearing. Decide early: do collapsed children have positions (parked at parent's location, simulation skips them) or are they fully absent from the simulation until expanded? The former is simpler and recommended.
- Aggregate edge rendering at scale is itself a performance concern. Batch draw them.
- The three-zone threshold model will need tuning. Ship it configurable, adjust with real graphs in hand.
- Animation timing is critical — too fast and the user loses track, too slow and interaction feels laggy. Target 300–500ms with ease-out.

## Notes for the implementer

This ticket is the make-or-break feature for large graph usability. Do not rush it. Prototype the animation and threshold behavior with a synthetic 500-node graph before integrating with the real schema. If the feel is not right at prototype stage, it will not be right in production either.
