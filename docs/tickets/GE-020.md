# GE-020 — Local persistence: Postgres via Docker + Drizzle + Hono

**Status:** DONE
**Phase:** Phase 3 — Scale (rescoped from "server-side graph storage + API layer")
**Effort:** L
**Depends on:** GE-003
**Blocks:** GE-023

## Summary

Replace the in-memory-only schema model with a Postgres-backed store so user edits survive page refreshes and multiple projects can coexist. Postgres runs in Docker for local development; the API runs as Vite dev-middleware using Hono; Drizzle provides the ORM layer. The resulting API surface is portable — if deployment happens later, swapping the host is configuration, not a rewrite.

## Context

Before this ticket, every change the user makes (node edits, new guided paths, accepted AI descriptions, OpenAPI merges) lives only in React state and evaporates on page refresh. `downloadSchema` / `readSchemaFromFile` (GE-010) provide a file-level save/load, but require explicit user action.

The original GE-020 scope proposed a generic "server-side storage + API layer" and was blocked on open strategic questions (hosting model, auth, multi-tenancy). Those questions are now answered by scoping tightly:

- **Hosting model**: local-first via Docker Compose; deployment deferred
- **Auth / multi-tenancy**: no auth, single user. Projects are isolated by `graphs.id`. Real auth is a future ticket.
- **Schema versioning**: latest-only. History comes later if it earns its keep.

This ticket delivers an MVP-complete persistence story that matches the actual usage (solo passion project, demo to team).

## Scope

### Infrastructure

- `docker-compose.yml` at repo root with a single `postgres:16-alpine` service on port 5432, bound to a named volume for persistence, with a simple password (env-configurable).
- `README.md` updated with `docker compose up` as a prerequisite.
- npm scripts for `db:up` / `db:down` / `db:reset` as convenience wrappers.

### ORM + schema

- Drizzle ORM configured (`drizzle.config.ts`), generating migrations to `drizzle/`.
- Schema lives in `src/server/db/schema.ts`. Tables:
  - `graphs` — `id` (UUID), `name`, `meta` (JSONB for `nodeTypes` + `linkTypes` + other meta), `created_at`, `updated_at`.
  - `nodes` — `id` (composite pk: graph_id + node_id), `graph_id` FK, `name`, `type`, `description`, `origin`, `parent`, `children` JSONB, `metadata` JSONB, `manual_overrides` JSONB, `collapsed`, `group_name`, `owner`.
  - `links` — composite pk + graph_id FK + all `Link` fields; `metadata` and `manual_overrides` as JSONB.
  - `paths` — composite pk + graph_id FK + `Steps` array as JSONB.
  - `annotations` — reserved table with the shape from v1.0 types, ready for GE-023 to land without a migration.
- First migration (`0001_initial.sql`) generated via `drizzle-kit generate`.

### API

- Hono app in `src/server/api.ts` exposing:
  - `GET    /api/graphs` — list `{ id, name, updated_at }` for project picker.
  - `POST   /api/graphs` — create new, optionally seeded with a `Schema` body (used by OpenAPI import "save as new project").
  - `GET    /api/graphs/:id` — full `Schema` assembled from joined rows.
  - `PUT    /api/graphs/:id` — replace full schema (idempotent; used by every save path).
  - `DELETE /api/graphs/:id` — remove the project.
- All write endpoints run the v1.0 `validate()` function before committing.
- Errors return JSON `{ error: { kind, message } }` with appropriate status codes.
- API handlers are pure over the db client — easy to unit-test.

### Vite integration

- `vite.config.ts` `configureServer` hook mounts the Hono app at `/api/*` during `npm run dev`. No separate dev process.
- Production deployment (later) extracts the same Hono app to a standalone Node server via `@hono/node-server` — zero code change.

### Client integration

- `src/api/client.ts` — small typed fetch wrapper: `listGraphs()`, `getGraph(id)`, `createGraph(body?)`, `updateGraph(id, schema)`, `deleteGraph(id)`.
- `GraphExplorer.tsx`:
  - On mount: read `?project=<id>` from URL; if missing, call `listGraphs()` and pick the most recently updated, else create a new one seeded with `INITIAL_SCHEMA`.
  - After `setSchema(next)`, debounce 500ms and `PUT` to `/api/graphs/:id`.
  - Project picker in the top bar (dropdown): switch, create, delete.
- Failure mode: if the API is unreachable (Docker stopped), fall back to the existing in-memory flow + a visible "Offline — changes won't persist" banner.

## Out of scope

- Auth / user accounts.
- Schema migration for end users (the db schema is declared via Drizzle migrations only; user data is preserved across app upgrades via JSONB fields).
- Real-time sync (GE-024 territory).
- Server-side merge. Merge stays client-side per GE-007 — the server is dumb CRUD.
- Deployment to a hosted Postgres. The Hono app is deployable, but this ticket does not commit to a hosting target.
- Backups / point-in-time recovery. Users can `docker compose down` + copy the volume.

## Acceptance criteria

- `docker compose up` then `npm run dev` boots both Postgres and the app; opening localhost:5173 shows the graph, loaded from the db.
- Creating a new project, editing it, and refreshing the page preserves all changes.
- Switching projects via the picker loads the correct schema.
- Deleting a project removes it from the picker + deletes its rows.
- With Docker stopped, the app gracefully falls back to the in-memory flow with the banner.
- `tsc --noEmit`, `npm test`, and `npm run build` all pass.

## Risks

- Drizzle's JSON column typing can be loose. Store the full domain-typed Schema via explicit `type`/`$inferSelect` annotations.
- Vite middleware runs in the same process as the dev server — long-running queries would block HMR. Keep API handlers fast; Postgres latency at localhost is sub-millisecond so this is fine.
- Node-pg native bindings sometimes fail on Apple Silicon — if so, swap to `pg`'s pure-JS mode or document the workaround.

## Notes for the implementer

Keep the API surface narrow (5 endpoints). Resist the urge to add `PATCH /nodes/:nodeId` etc. — the full-schema PUT is simple, idempotent, and avoids partial-update complexity. If the schema eventually grows beyond a few hundred KB, revisit partial updates then.

Drizzle's `pg` driver: `pnpm add drizzle-orm pg && pnpm add -D drizzle-kit @types/pg`. Hono: `pnpm add hono`.

The API should export a pure `createApp(db)` factory so it can be re-mounted in both dev (Vite middleware) and prod (standalone Node server).
