# GE-006 — OpenAPI parser (pure function)

**Status:** DONE
**Phase:** Phase 1 — Foundation
**Effort:** M
**Depends on:** GE-002, GE-003, GE-005
**Blocks:** GE-007, GE-008

## Summary

A pure function that takes an OpenAPI v3.x specification and returns a candidate schema (nodes + links + suggested groups) conforming to the v1.0 shape. No side effects, no UI, no merging — this ticket only covers the translation layer.

## Context

Manually authoring a graph of a non-trivial system is the single biggest friction point preventing Graph Explorer from being useful. Almost every backend worth mapping already publishes an OpenAPI spec. Translating that spec into graph nodes and links is a high-leverage automation — the user describes their system once (in OpenAPI) and the graph follows.

This ticket implements only the pure translation. Merging the output into an existing schema, handling conflicts, and surfacing to the UI are separate concerns (GE-007 and GE-008).

## Scope

Given an OpenAPI v3.x spec (JSON or YAML, already parsed into a JS object by the caller), produce a candidate schema containing:

- **Database-type nodes** for every entry in `components.schemas`. The node name matches the schema name. The description falls back to the schema's `description` field when present, otherwise a sensible default.
- **API-type nodes** for every path × method combination. The node name is `METHOD /path`. The description falls back to `operation.summary` or `operation.description`.
- **Dependency-type links** for every `$ref` found inside a schema's properties, pointing from the referencing schema to the referenced schema. The link label names the property (e.g., `ownerId →`). The description is human-readable.
- **Data-flow-type links** for every request body or response body that references a schema, pointing from the API node to the schema node. Direction: API node → schema for request bodies, schema → API node for response bodies. If both, create both links.
- **Groups** derived from OpenAPI `tags`. An endpoint's first tag becomes its group. Schemas with no natural tag fall into a default group (configurable, default `data`).

Every generated node and link must carry `origin: "auto:openapi"`. Every generated link must have a deterministic, stable ID derived from its source, target, and type (so re-parsing the same spec produces identical IDs — required for the merge engine).

The function signature, input shape, and return shape are the implementer's choice but must be documented in JSDoc / TSDoc on the exported symbol.

## Out of scope

- File reading, file upload, or URL fetching of the spec. The function takes an already-parsed object.
- YAML parsing — use a library if needed, or require the caller to parse YAML separately. Not this ticket's concern.
- Merging with an existing schema (GE-007).
- Any UI (GE-008).
- Parsing OpenAPI v2 (Swagger). v3 only.
- Handling non-standard OpenAPI extensions (`x-*` fields) — ignore them.

## Acceptance criteria

- The parser accepts a realistic OpenAPI v3 spec (at least 20 paths, at least 10 schemas, multiple tags, cross-schema references) and produces a valid v1.0 candidate schema.
- Running the parser twice on the same input produces identical output (determinism).
- All generated nodes and links have `origin: "auto:openapi"`.
- The parser's output passes the schema validator from GE-003.
- Unit tests cover: a minimal spec, a spec with `$ref` chains, a spec with polymorphic bodies (`oneOf` / `anyOf`), a spec missing optional fields, and an empty spec.
- The function has no side effects and does no I/O.
- Malformed specs are rejected with a clear error, not silently producing garbage.

## Risks

- OpenAPI is permissive. Real-world specs have inconsistencies (missing `operationId`, ambiguous `$ref` targets, inline schemas). The parser must handle these gracefully rather than crashing.
- Deterministic ID generation is harder than it looks — node names can collide between tags, methods, and schemas. Namespace IDs by type (`api_`, `schema_`, etc.) to prevent collisions.
- `$ref` can point to remote files. This ticket does not follow remote refs — log a warning and skip.

## Notes for the implementer

Keep this function pure and well-tested. It is the easiest module in the project to write tests for and the hardest to debug when wrong. Sink the time into edge cases now — every downstream merge bug will trace back to ambiguity here.
