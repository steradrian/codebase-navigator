# GE-007 — Schema merge engine (non-destructive)

**Status:** DONE
**Phase:** Phase 1 — Foundation
**Effort:** M
**Depends on:** GE-003, GE-006
**Blocks:** GE-008, GE-025, GE-026

## Summary

A pure function that merges a newly imported candidate schema into an existing working schema without destroying human-authored content. Surfaces conflicts rather than resolving them silently.

## Context

An OpenAPI importer that overwrites manual annotations on every re-run is worse than no importer. Users will invest hours adding ownership, descriptions, guided paths, and business-logic annotations on top of the auto-generated scaffold. That investment must survive the next import.

The merge engine is the contract that makes auto-import trustworthy. It is also small, pure, and testable — the perfect kind of code to get right on the first attempt.

## Scope

Implement a merge function that takes an existing v1.0 schema and a candidate v1.0 schema (from GE-006 or a future importer) and returns:

- A merged schema.
- A conflict report describing anything that could not be safely merged.

Merge rules:

- **New auto nodes / links** (present in candidate, absent in existing) are added.
- **Manual nodes / links** (existing with `origin: "manual"`) are preserved untouched, even if a candidate with the same ID exists.
- **Auto nodes / links** (existing with `origin: "auto:*"`) are updated to match the candidate. Fields that are manually overridden on an auto node (see below) are preserved.
- **Manually edited fields on auto-generated entities** must be preserved. Concretely: every node and link carries per-field override tracking (either a `manualOverrides: string[]` list on the node/link, or a sibling field on the schema — implementer's choice, but document it). When a candidate tries to update an overridden field, the manual value wins and the discrepancy goes into the conflict report.
- **Auto entities that no longer appear in the candidate** are removed from the merged schema. This is the "auto is authoritative for auto" rule — if the backend dropped an endpoint, its node goes away. Unless a manual override exists, in which case the node is kept and flagged in the conflict report.
- **Guided paths and annotations are always preserved**. They reference nodes, so if a referenced node is about to be removed, the merge blocks the removal and logs a conflict.

The conflict report is a structured list — each entry names the entity, the conflict type, and the fields involved. It is the UI's job (GE-008) to render this for user review.

## Out of scope

- UI surfaces for resolving conflicts — GE-008.
- Persistence of the merged schema — the output is a pure value; the caller decides what to do with it.
- Three-way merge (ancestor + local + remote). MVP does a two-way merge: existing vs candidate.
- Automatic conflict resolution. The engine surfaces conflicts; the user or UI resolves them.

## Acceptance criteria

- Unit tests cover, at minimum:
  - Empty existing + non-empty candidate → candidate is the result.
  - Non-empty existing + empty candidate → existing is the result, no data lost.
  - Candidate adds a new auto node → merged schema contains it.
  - Candidate updates an auto node's description → updated description appears in merged schema.
  - Manual override on an auto node's description → candidate's new description goes into the conflict report; the override persists in the merged schema.
  - Candidate drops an auto node that is referenced by a manual guided path → conflict logged, node preserved.
  - Manual node with the same ID as a candidate auto node → manual node preserved, conflict logged.
- The merge function is pure: running it twice with the same inputs yields identical outputs.
- The merged schema passes the v1.0 validator from GE-003.
- The conflict report is typed (no free strings) and serializable to JSON.

## Risks

- The "manual override tracking" design decision is load-bearing. Choosing the wrong representation makes every downstream feature harder. Think carefully: per-field override list on the entity vs. a side table vs. comparing against the last-known-auto snapshot. Document the decision in the ticket's closing notes.
- Guided path preservation creates an edge case: if a path references a node that the candidate says should be deleted, what happens on the next re-import? Spec: block the deletion, keep the node with its prior auto state, log a conflict, and let the user decide.
- Performance does not matter at MVP scale (hundreds of nodes). Do not pre-optimize.

## Notes for the implementer

This ticket is the quiet backbone of the auto-import experience. Get the rules right and the importer UX feels magical. Get them wrong and users lose trust after the first re-import. Cover every acceptance-criteria case with a unit test before wiring anything to the UI.
