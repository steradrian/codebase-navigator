# GE-028 — Health overlays (Sentry / Datadog / etc.)

**Status:** TODO
**Phase:** Phase 4 — Ecosystem
**Effort:** L
**Depends on:** GE-003, GE-020
**Blocks:** —

## Summary

Pull live observability data (error rates, latency, deploy frequency, alerts) from external monitoring tools and overlay it on graph nodes as color or badge indicators. A node that is currently paging shows red; a node that was deployed this morning shows a fresh badge.

## Context

A static architecture graph is interesting; a live architecture graph is operational. Engineers already keep Grafana dashboards, Sentry error pages, and Datadog service maps open during incidents. Graph Explorer has an advantage none of them have: structural context. A Sentry error on `/api/reviews` is more meaningful when the graph shows that seven features depend on that endpoint.

This ticket is deliberately scoped as an integration framework — one provider end-to-end, with a clear extension path for more.

## Scope

- A provider interface for fetching health metrics per node. Implement one concrete provider for MVP — recommend Sentry (rich API, widely used) or Datadog.
- Configuration mapping graph nodes to provider entities (e.g., "node `api_rest` maps to Sentry project `backend-api`"). Matching rules can be a mix of explicit mapping and naming conventions.
- A polling or push mechanism for keeping data fresh. Poll on an interval for MVP; push (webhook-driven) post-MVP.
- Rendering:
  - Node color tint based on health state (green / yellow / red), overriding the default type color while health overlay is active.
  - A compact badge on nodes with active alerts, deploys in flight, or elevated error rates.
  - Detail panel section showing current and recent metrics.
- A global toggle to turn the overlay on or off.
- Graceful degradation when the provider is unreachable — show a disconnected state, not fake-green.

## Out of scope

- Bidirectional integration (creating incidents from the graph, acknowledging alerts). Read-only for MVP.
- Historical playback (scrub through time to see how health evolved). Post-MVP.
- Alerting or paging from within Graph Explorer.
- Multiple simultaneous providers in a single render. MVP supports one active provider at a time.
- Custom metric definitions. Use whatever the provider exposes.

## Acceptance criteria

- With the chosen provider configured, nodes mapped to provider entities show correct health state.
- The overlay respects the polling cadence and updates visibly when health changes.
- The toggle hides and shows the overlay cleanly.
- Missing or unmapped nodes render neutrally, not as "unhealthy."
- Provider credentials are handled securely — documented path for configuration.

## Risks

- Provider APIs are rate-limited. Poll sparingly; cache aggressively.
- Node-to-entity mapping is the hardest UX problem in this ticket. Name-matching fails often. Provide a manual override in the UI.
- Color accessibility — red/green does not work for colorblind users. Include non-color indicators (icons, text).

## Notes for the implementer

Pick one provider. Ship it. Resist the temptation to build a generic plugin system before you know what the second and third providers actually need. The first integration will teach you what the interface should look like.
