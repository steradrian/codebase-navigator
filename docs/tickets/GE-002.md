# GE-002 — Vitest + test harness setup

**Status:** DONE
**Phase:** Scaffolding
**Effort:** S
**Depends on:** GE-001
**Blocks:** GE-006, GE-007 (importer and merge engine are pure functions and must be test-covered)

## Summary

Set up Vitest with a minimal first test so that every subsequent ticket dealing with pure logic (parsers, merge engine, schema validators) has an obvious place to add coverage.

## Context

Graph layout, importers, and schema manipulation are notoriously easy to break silently — a missing field survives for weeks before someone notices a rendering glitch. The MVP plan adds several pure-function modules (OpenAPI parser, merge engine, schema validators) that are cheap to test and expensive to debug in the renderer.

Getting the harness in place now, with one real test, means every future ticket starts with "and write the tests for it" as a low-friction default rather than a chore.

## Scope

- Add Vitest as a devDependency.
- Add a test script to `package.json` (`test`, and optionally `test:watch`).
- Configure Vitest to work alongside Vite — the existing Vite config should drive the test environment.
- Add a single real test against an existing pure function (for example, a selector or helper in the current codebase, or a trivial `ForceSim3D` construction test). This is a smoke test that proves the harness is wired correctly.
- Add a `README.md` note — one paragraph — explaining how to run tests. Keep it short; do not write exhaustive testing docs.
- Ensure `tsc --noEmit` still passes with test files included.

## Out of scope

- Visual regression / snapshot testing of the Three.js renderer. Skipped intentionally — flaky, slow, low signal. Revisit post-MVP if needed.
- Playwright / E2E setup. Post-MVP.
- Coverage thresholds or CI enforcement. Land the harness first; add gates when there is something worth gating on.
- Testing existing UI components. The existing `GraphExplorer` is too tangled to test meaningfully; wait for it to be decomposed in later tickets.

## Acceptance criteria

- `npm test` runs and passes.
- At least one real assertion runs against real source code (not a placeholder `expect(true).toBe(true)`).
- Test files live in a predictable location (co-located `*.test.ts` next to source, or a top-level `tests/` directory — pick one and document it).
- The test uses TypeScript and benefits from the types established in GE-001.

## Risks

- Vitest + Three.js can interact badly if a test accidentally imports the full renderer (DOM / WebGL not available in jsdom). Avoid by keeping tests pointed at pure modules.
- Over-engineering this ticket is the main failure mode. One test is enough.

## Notes for the implementer

Resist the urge to add a test matrix, custom matchers, or a testing-library wrapper for components that do not exist yet. The purpose of this ticket is to remove the friction of "where do tests even go?" for the tickets that follow. One passing test, five minutes of README, and done.
