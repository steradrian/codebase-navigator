# GE-104b — Filter rail: add domain facet

**Status:** TODO
**Phase:** UX / Visualization
**Effort:** S
**Depends on:** GE-104 (filter rail), GE-115 (domain field on Node)
**Blocks:** —

## Summary

Extend the filter rail with a fourth facet group — **Domain** — between Type and Entity. Same multi-select + count semantics as existing facets. Selecting `payments` narrows to the whole Payments slice of the system; combining with Entity narrows further within that slice.

## Context

GE-115 introduces the two-level model: nodes carry both `entity` (fine-grained, from `components.schemas`) and `domain` (coarse, from OpenAPI tags). The filter rail today has Type, Entity, Origin. Adding Domain lets users think at either granularity without going through the entity facet's long list — and lets them do domain-scoped queries like "Payments + ui-type only" in one glance.

The filter rail's state model was designed for this exactly: `{ types, entities, origins }` as `Set<string>` becomes `{ types, domains, entities, origins }`. No new logic — one more facet.

## Scope

- Add `domains: Set<string>` to the filter state.
- Compute domain counts from `schema.nodes` via `useMemo`, same pattern as entity counts.
- Render a new facet group "Domain" between Type and Entity. Matches the visual style of the existing groups: collapsible header, count badges, master-checkbox, "Unclassified" bucket for nodes without `domain`.
- Update the `isFilteredIn(node)` helper to apply domain check alongside the others. Semantics stay AND-across-groups, OR-within-a-group.
- URL state (GE-022): serialize `domains` alongside `types` / `entities` / `origins`. Same encoding.
- When GE-106's color-by-entity mode is active, the legend shows entities; when the new (future) color-by-domain mode is added, the legend swaps to domains. For now, don't ship color-by-domain — just the filter.

## Out of scope

- Color-by-domain rendering mode. Separate small ticket if we want it. Likely GE-106b.
- Nested checkbox hierarchy (check Payments domain → auto-check all its entities). Flat interaction is fine; domains and entities are independent facets joined by AND.
- A "domain-only" view that hides the entity facet. Users who want coarse filtering just leave the entity group with all boxes checked.

## Acceptance criteria

- Import admin-dashboard spec. Rail shows 6 domain entries with counts: customer (N₁), wallet (N₂), payment (N₃), aggregator (N₄), bonus (N₅), auth (N₆) + Unclassified.
- Select `payment` → graph dims all nodes where `domain !== 'payment'`.
- Select `payment` AND select entity `customer` → empty intersection → graph shows zero nodes (correct — there are no payment-domain customer-entity nodes). Not a bug, a correct empty result.
- Select `payment` AND entity `payment` → shows only the Payment-entity nodes within the Payments domain.
- URL round-trips: link with `?domain=payment,bonus&entity=payment` lands a new tab on the same filtered view.
- Clear filters resets all four facets.

## Risks

- Users treating domain + entity as redundant ("isn't payment domain the same as payment entity?"). The entity filter is inclusion by the fine-grained entity. The domain filter is inclusion by the OpenAPI grouping. They overlap in this spec but aren't identical (Wallet domain contains Account entity; Bonus domain contains bonus-issue, freespin-bonus, comp-point, rakeback — multiple entities). Help text on the facet header: "Domain = OpenAPI tag. Entity = specific schema."
- Performance: four set-based membership checks per node per frame. Still cheap at 10k nodes; bench only if it regresses.

## Notes for the implementer

`FilterRail.tsx` is where the facet lives. Current `Filters` type is `{ types, entities, origins }`. Adding `domains` is a mechanical refactor — search/replace plus the new count memo plus a new group render. Keep the existing group component (`FacetGroup` or similar) and just pass the new list.

`isFilteredIn` currently does three inclusion checks. Add a fourth. Unit test to ensure AND-across and OR-within still hold.

URL state schema: add a `d=<csv>` param mirroring the existing `e=<csv>`. Parser + serializer both need a small edit.
