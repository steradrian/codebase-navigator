# GE-114 — Backfill entities on load for pre-v1.1 schemas

**Status:** TODO
**Phase:** UX (bug / data migration)
**Effort:** S
**Depends on:** GE-103 (entity extractor)
**Blocks:** GE-111, GE-112, GE-113 (they silently no-op without this)

## Summary

Schemas stored before GE-103 shipped (schema version `1.0`, no `meta.entities`, no `entity` field on nodes) are loaded from the API as-is. Every entity-aware feature — color-by-entity, entity filter in the rail, entity chips, legend-by-entity — silently does nothing on those graphs. Run `backfillEntities()` at the load boundary when entities are absent, and upgrade the stored version on the next save.

## Context

Discovered when inspecting the `Ann test` graph in Postgres (615 nodes, 1759 links). `meta.version` was still `1.0`, `meta.entities` missing, `0/615` nodes had `entity` set. The extractor would assign entities to 612/615 and surface 6+ real entities (`dashboard`, `bonus`, `ui`, `player-detail`, `auth`, `payment`). None of that was visible in the UI because the raw schema from the API never went through the extractor.

Fresh imports (OpenAPI / codebase paste) already run the extractor. This ticket covers the load path — graphs that predate the v1.1 schema.

## Scope

- On any API read that returns a full schema (`loadProject`, `loadSchema`, or wherever the main fetch boundary is — grep for where the client receives a `Schema` from the server), check `schema.meta.version` and `schema.meta.entities`.
- If `version !== SCHEMA_VERSION` OR `meta.entities` is missing/empty, run `backfillEntities(schema)` before handing the schema to React state.
- The next save (any mutation that writes the schema back) persists the upgraded shape — `meta.version = SCHEMA_VERSION`, `meta.entities` populated, nodes carrying `entity`. No separate migration endpoint.
- Do not rewrite a node's entity if it already has one (the extractor already respects this — verify).

## Out of scope

- A "re-extract entities" button for users who want to regenerate after improving the extractor. Future.
- Schema v1.0 → v1.1 migration for fields beyond entities (there are none right now, but if the schema continues to evolve this hook becomes the natural home).

## Acceptance criteria

- Load the existing `Ann test` graph from the DB. Entity filter, legend-by-entity, and color-by-entity all work without any manual action.
- The review banner (from GE-103) appears after load if entities were freshly backfilled and not yet reviewed.
- Save the schema once. Re-load. `meta.version` is now `1.1`, `meta.entities` is populated, and backfill does NOT run a second time.
- Fresh imports still behave the same — no double-extraction.

## Risks

- If the user has a graph where entity extraction would produce noise (auto-generated paths with misleading filenames), backfilling silently on load surprises them. Mitigation: the review banner surfaces the new entities and lets the user merge/rename, same as a fresh import.
- Don't block UI render on backfill — it's O(nodes) with trivial per-node cost, but for a 10k-node graph that's still measurable. Run synchronously before setState is fine; revisit if it ever shows up in a profile.

## Notes for the implementer

Gate purely on `meta.entities` being absent — checking `version !== SCHEMA_VERSION` is a belt-and-suspenders condition that also catches any future migrations. Put the call at the single place where a schema enters the React tree from the API; do not scatter it across call sites.
