# GE-011 — Group hull visualization

**Status:** DONE
**Phase:** Phase 1 — Foundation
**Effort:** M
**Depends on:** GE-003
**Blocks:** —

## Summary

Render translucent 3D volumes around each group of nodes so visual hierarchy is readable at a glance, even without full semantic zoom.

## Context

Today, nodes that share a `group` cluster together via the force simulation, but there is no explicit visual indication of the grouping. The viewer must infer it from proximity, which breaks down the moment nodes from different groups happen to sit near each other. For graphs of more than ~30 nodes, the result feels like a hairball.

Group hulls are the minimum viable visual hierarchy — a cheap, immediate improvement to readability that also lays groundwork for semantic zoom (GE-013). This is not clustering logic, it is just drawing a shape around the cluster the simulation already produces.

## Scope

- For each group in the current schema, compute a 3D convex hull (or a simpler bounding volume — sphere, box — at the implementer's discretion) that wraps all member nodes.
- Render the hull as a translucent mesh with the group's color or a muted derivation of it. Opacity low enough (~10–15%) that the hull frames the group without obscuring nodes or links.
- Label the group with its name, floating near the top or centroid of the hull. Label visibility follows the same fade-on-selection pattern already in use for node labels.
- Hulls update as the simulation progresses (nodes move → hull follows). This must not tank framerate — recompute on a throttled interval (every N frames) rather than every tick.
- A toggle to hide hulls entirely for users who prefer the cleaner view.

Decision on hull type is the implementer's: convex hull is most accurate but most expensive; bounding sphere is cheapest; bounding box is a middle ground. Pick based on visual quality at MVP scale (~50–200 nodes) and document the choice.

## Out of scope

- Cluster collapse / expand behavior — that is GE-013.
- Interactive hull actions (click hull to select group, drag hull to move group) — defer.
- Overlapping-group handling. If two groups visually overlap in 3D space, accept the visual messiness for MVP. Force simulation should keep them mostly separate anyway.
- Hulls for the `parent`/`children` hierarchy (nested groups). MVP only draws one level — the `group` field.

## Acceptance criteria

- Every group in the demo schema is visually framed by a hull that moves with its nodes.
- Hulls do not tank framerate at the current MVP scale.
- Group names are legible floating near each hull.
- The hull toggle works and the preference persists within the session.
- When no nodes have a `group`, no hulls are rendered — no crash, no empty geometry.
- Hull rendering respects selection/highlight states: selecting a node inside a hull should not make the hull obscure the selection.

## Risks

- Convex hull computation is O(n log n) per group per update. At MVP scale this is negligible, but the implementer must not recompute on every frame — throttle to 30fps or coarser.
- Transparent meshes in Three.js require correct render ordering to avoid z-fighting and visual artifacts. Expect to spend time tuning render order and depth settings.
- Visual overload is a real risk — 20 colored hulls can feel chaotic. Err toward subtle.

## Notes for the implementer

This is a "vibes" feature. Framerate and correctness matter, but the real acceptance test is a screenshot: does the graph feel more structured with the hulls on than off? If not, tune until yes before closing.
