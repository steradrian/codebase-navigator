# GE-018b — Move force simulation into a Web Worker

**Status:** TODO (deferred from GE-018)
**Phase:** Post-MVP scale (follow-up to GE-018)
**Effort:** L
**Depends on:** GE-018 (Barnes-Hut), GE-003
**Blocks:** —
**Trigger:** Real-world graph exceeds ~500 nodes and main-thread profiling shows `sim.tick()` dominates frame time.

## Summary

Relocate `ForceSim3D` (with its Barnes-Hut implementation from GE-018) into a dedicated Web Worker. The main thread's render loop reads node positions from a snapshot updated by the worker on a throttled cadence. Unblocks smooth interaction at 1000+ node scale.

## Context

GE-018 shipped Barnes-Hut in-thread as the high-leverage piece of the original ticket. The worker piece was deferred because:

- Barnes-Hut alone reduces per-tick cost from O(n²) to O(n log n) — at MVP scales the simulation is no longer a bottleneck.
- Moving to a worker changes the render loop's synchronous read of `sim.nodes` into an asynchronous snapshot-based pattern, which touches every visual mode (selection, path, blast, diff, collapsed-cluster rendering, hull centroid computation) in `GraphExplorer.tsx`.
- There is no workload today that justifies the refactor risk.

Ship this when the workload appears.

## Scope

- Move `ForceSim3D` and its Barnes-Hut helpers into a Web Worker (`src/workers/forceSim.worker.ts`).
- Main-thread `SimProxy` class provides the same public API as today's `ForceSim3D` (`tick`, `reheat`, `getNode`, `getConnectedIds`, `setMode2D`, `mode2D`, `alpha`, etc.) but dispatches to the worker.
- Position updates flow main ← worker via `SharedArrayBuffer` when `crossOriginIsolated` is true; fall back to structured-clone `postMessage` snapshots otherwise. Document which path is active via a runtime log.
- Animation loop reads the proxy's position snapshot per frame; no change to `GraphExplorer.tsx` visual logic.
- Worker lifecycle: create on scene setup, terminate on teardown. Rebuild on schema replacement (consistent with current scene-setup useEffect dep).
- Drag-to-reposition (if added later) posts updates back to the worker.

## Out of scope

- GPU-based (WebGPU) force computation. A separate future ticket.
- Replacing the force simulation with a different layout algorithm (hierarchical, radial, etc.).
- Adding a configuration UI for worker behavior — use sensible defaults.

## Acceptance criteria

- `GraphExplorer.tsx` compiles and runs unchanged after swapping `new ForceSim3D(...)` for `new SimProxy(...)`.
- At 500 nodes: 60fps with simulation actively running.
- At 2000 nodes: 30fps+ with interactive responsiveness.
- Fallback path (no `SharedArrayBuffer`) works end-to-end — verify by deploying without COOP/COEP headers.
- Existing 85+ tests continue to pass (unit tests for the sim stay in-thread since they don't exercise the worker boundary).

## Risks

- `SharedArrayBuffer` requires cross-origin isolation. Document the deployment prerequisite (COOP: same-origin, COEP: require-corp) or accept the fallback.
- Worker lifecycle bugs are quiet — aggressive disposal + recreation on schema change.
- Barnes-Hut implementation, when ported, must produce bit-identical results to the in-thread version for small inputs. Golden test against the existing `ForceSim3D` for regression safety.

## Notes for the implementer

Keep the worker's message protocol narrow and versioned. A `{kind: 'tick', alpha}` request / `{kind: 'positions', buffer}` response is enough for MVP — resist generalizing.
