# GE-008 — OpenAPI import UI

**Status:** DONE
**Phase:** Phase 1 — Foundation
**Effort:** M
**Depends on:** GE-006, GE-007
**Blocks:** —

## Summary

A user-facing surface for loading an OpenAPI spec, previewing what the import will change, reviewing conflicts surfaced by the merge engine, and confirming the merge.

## Context

GE-006 parses OpenAPI into a candidate schema. GE-007 merges candidates non-destructively and surfaces conflicts. This ticket is where those capabilities meet the user. The UX of this moment defines whether auto-import feels like a power tool or a trust-destroyer: users must see exactly what will change before they commit.

## Scope

An import flow with the following stages:

1. **Source selection.** The user provides an OpenAPI spec either by file upload (JSON or YAML) or by pasting text into a textarea. URL fetch is optional; if included, stay client-side (no server proxy).
2. **Parse + validate.** The file is parsed; errors are shown inline with a helpful message. On success, the parser from GE-006 runs to produce a candidate schema. Validation errors from GE-003's validator are also surfaced here.
3. **Preview.** A side-by-side (or tabbed) view shows: nodes being added, nodes being updated, nodes being removed, links being added / updated / removed, and the full conflict report. Conflicts are visually distinct — they require acknowledgment before the merge can proceed.
4. **Conflict review.** For each conflict, the user sees the two versions (current vs. candidate) and picks a resolution: keep current, accept candidate, or (for manually overridden fields) acknowledge the divergence and continue. The UI must not force users to resolve every conflict — "continue without changes" is always an escape hatch.
5. **Confirm.** The user clicks confirm and the merged schema replaces the in-memory working schema. The graph re-renders to reflect the new data.

## Out of scope

- Persistence of the merged schema to disk / server — that belongs to GE-010 (export) or GE-020 (server storage).
- Scheduling recurring imports — that is GE-025 (CI/CD integration).
- Auth or credentialing for remote spec URLs.
- Visual diff of individual field values beyond showing "before / after" text. No syntax-highlighted JSON diffs — too much work for MVP.

## Acceptance criteria

- A user can load a real OpenAPI spec from file, paste, or URL and see a preview of the resulting graph changes.
- Conflicts surfaced by GE-007 are visible in the preview and cannot be silently ignored — the user must see them before confirming.
- Confirming the merge updates the in-memory schema and the rendered graph immediately.
- Canceling the import leaves the graph in its prior state.
- Parse errors and schema-validation errors are surfaced with clear messages, not silent failures or generic "something went wrong."
- The flow is accessible by keyboard — no mouse-only interactions.

## Risks

- Preview UX can balloon. Stay minimalist: lists of IDs with type badges are sufficient for MVP. Do not attempt to preview the new graph layout visually.
- Large specs (hundreds of endpoints) will produce large preview lists. Paginate or virtualize if needed — do not let the browser freeze.
- The conflict UI is the most subtle part. Err toward clarity over density — conflicts should be impossible to miss.

## Notes for the implementer

Spend your design budget on the conflict review step. Everything else is plumbing. The first time a user re-imports after adding manual annotations is the moment they decide whether to trust this feature.
