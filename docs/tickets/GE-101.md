# GE-101 — Navigation history (back / forward / breadcrumb)

**Status:** DONE
**Phase:** Polish / UX
**Effort:** S
**Depends on:** —
**Blocks:** —

## Summary

Add browser-style back / forward navigation across node selections. Users can trace their way back through the nodes they've explored, and a breadcrumb chip row shows the trail so they can jump to any earlier point without blindly clicking "back."

## Context

Currently a user selects `A`, then clicks a connection and lands on `B`, then `C`. To get back to `B` they have to remember what `B` was and hunt for it in `C`'s connection list. This breaks narrative flow — you're reconstructing instead of retracing. The fix is the browser-tab metaphor everyone already knows.

## Scope

- Maintain an in-memory history stack of selected node IDs. Entries are pushed when the user explicitly selects a node (click, search result, connection-row click, NL query result). Entries are NOT pushed for internal camera moves (e.g. entering path mode, forceOpenChain expansions).
- When the user uses back / forward, the stack pointer moves without mutating the history. If they THEN select a new node, the "forward" portion is discarded (browser semantics).
- Floating overlay pill at the bottom-center of the canvas. Layout: `◀  chip-1 · chip-2 · … · chip-N  ▶`. Hidden when history is empty.
- `◀` / `▶` buttons disabled appropriately at the ends of the stack.
- Breadcrumb chips show up to the most recent ~5 entries. Clickable — jumping back via a chip moves the pointer to that entry (same as repeated "back" but faster).
- Keyboard shortcuts: `Alt + ←` / `Alt + →` trigger back/forward. `Cmd+[` / `Cmd+]` on macOS as alternative.
- Works in all modes (info, path, blast) — back/forward navigates selection only, not modes.
- History does NOT cross project boundaries. Switching projects resets the stack.

## Out of scope

- Persisting history across page refreshes. Session-only is fine; URL state already captures the current selection via GE-022.
- Undo/redo for schema edits. Different feature.
- Recording edge traversals separately from node selections.

## Acceptance criteria

- Select A → B → C, press back twice, land on A.
- After going back, press forward twice, land on C.
- At A, go back (disabled — at start), forward enabled to B.
- Clicking a breadcrumb chip moves the pointer directly there.
- History overlay is hidden when the user has only ever selected one node (or none).
- Keyboard shortcuts work without trapping editable-input keystrokes.
- Switching projects clears history.
- The navigation control does not overlap the side panel, legend, or any existing top-bar element. At small viewports it gracefully shrinks chips or hides older ones.

## Risks

- Overlay placement at bottom-center may conflict with the legend (also bottom-left). Test at different viewport widths; chip row can reserve horizontal space that respects the legend's footprint.
- Auto-select triggered by side effects (e.g. paths starting and selecting their first step) should NOT push to history, or "back" takes you into weird mid-path states. The implementing agent must carefully gate pushes by "was this a user action."

## Notes for the implementer

Store the history in a ref, not React state, to avoid re-render churn on every selection. Fire a single React state update (an incremented counter) when the overlay needs to re-render. Keep the push logic in exactly ONE place — a `navigateTo(nodeId, { fromNavigation: boolean })` helper that every selection path funnels through.
