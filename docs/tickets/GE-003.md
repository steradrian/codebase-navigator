# GE-003 — Schema v1.0 migration

**Status:** DONE
**Phase:** Scaffolding
**Effort:** M
**Depends on:** GE-001
**Blocks:** GE-006, GE-007, GE-011, GE-013, GE-015 and every later ticket that touches the data model

## Summary

Migrate the schema shape from the current v0.2 (flat nodes, flat links, minimal metadata) to v1.0 (hierarchical, typed links, origin tracking, stable IDs on links, per-node metadata). This is invisible to the user but unblocks almost every feature after it.

## Context

The v0.2 schema was sufficient for the prototype but carries structural gaps that would force retrofits if ignored:

- Links have no stable ID, so annotations (GE-023) and diff tracking (GE-016) have nothing to target.
- There is no `parent` / `children` relationship, so semantic zoom (GE-013) is impossible.
- There is no `origin` field (`manual` vs `auto:openapi` vs `auto:codebase`), so the non-destructive merge engine (GE-007) cannot distinguish human-authored content from machine-generated content.
- Link categories are typed as free strings today. Formalizing them into a `linkTypes` registry (mirroring `nodeTypes`) enables consistent visual styling and validation.
- Path steps cannot express timing or async-ness.

The cost of fixing these in one coordinated migration is much lower than fixing them one at a time as each feature bumps into them.

## Scope

Define, implement, and migrate to the v1.0 schema. The final shape must include, at minimum, the following additions or changes versus v0.2:

- `meta` gains `lastUpdated` and a `sources` array tracking which importers have contributed data.
- A new top-level `linkTypes` registry, parallel to `nodeTypes`, carrying color, label, and visual-style hints (dashed, animated, etc.). Existing link type strings (`data_flow`, `dependency`, `triggers`) become keys in this registry.
- Every link gets a stable `id` (generated if not present in existing data).
- Every link gets an `origin` field distinguishing manual from auto-generated.
- Every link optionally carries a `weight` (for visual thickness and impact analysis scoring) and a `metadata` object with free-form extension points.
- Every node gets an `origin` field, an optional `parent` reference, an optional `children` array, a `collapsed` boolean (defaulting to false), and a `metadata` object with at least `lastModified`, `health`, `team`, `tags`, and `externalUrl` as defined fields.
- Paths gain an optional `category` and steps gain an optional `duration`.
- A new top-level `annotations` array is reserved (empty in MVP) for GE-023.

Deliverables:

- Updated TypeScript types reflecting v1.0. These types are the canonical source of truth — all future code reads from them.
- A migration function that takes a v0.2 schema and returns a v1.0 schema, filling in sensible defaults (origin: `manual`, no parent, empty children, etc.).
- The existing demo schema (`schema.js` / `.ts`) migrated in place so the app still runs.
- A schema version field and a validator that rejects malformed schemas with a clear error.
- Unit tests (using GE-002's harness) for the migration function and validator covering the happy path and at least three malformed inputs.

## Out of scope

- Any UI surface reflecting the new fields. Group hulls (GE-011), semantic zoom (GE-013), and health overlays (GE-028) consume this data in their own tickets.
- The merge engine itself — that is GE-007.
- Persisting schemas to a server — this ticket stays client-side, in-file.
- Renaming `source_meta` — that is GE-005's job and happens before this ticket in execution order.

## Acceptance criteria

- The app runs against the migrated demo schema with no visible regression.
- `tsc --noEmit` passes with the new types.
- The migration function, when given the pre-migration `schema.js`, produces valid v1.0 output.
- The validator catches at least these failure modes: duplicate node ID, link referencing missing node, invalid type reference, missing required field on node or link.
- Tests pass.

## Risks

- Tempting to over-design the metadata shape. Resist — the doc lists the fields we need; add only those. Future fields can be added as optional without breaking consumers.
- The `parent` / `children` relationship must be consistent (if A lists B as a child, B must list A as its parent). The validator must enforce this or silent corruption is guaranteed.
- Link IDs generated at migration time must be deterministic (e.g., derived from source + target + type) so re-running migration does not churn IDs and invalidate future annotations.

## Notes for the implementer

This ticket is boring but load-bearing. The quality of the types you write here shapes every downstream ticket. Spend the time to get names right. Err toward explicit union types (e.g., `type Origin = "manual" | "auto:openapi" | "auto:codebase"`) rather than free strings — the cost of adding a new origin later is trivial, the cost of living with `string` is permanent.
