# GE-026c — Link codebase UI to OpenAPI endpoints

**Status:** DONE
**Phase:** Phase 4 — Ecosystem (follow-up to GE-006 + GE-026)
**Effort:** S–M
**Depends on:** GE-006 (OpenAPI parser), GE-026 (codebase parser), GE-007 (merge engine not required — additive-only)
**Blocks:** —

## Summary

After users import both an OpenAPI spec and a codebase, the two ends of the stack show up as disconnected clusters. This ticket adds a third pass that extracts API calls from source files (`client.GET('/admin/x')`, `fetch(…)`, hook-to-function indirection) and emits `data_flow` edges from code nodes to their corresponding API operation nodes. Result: the graph shows how frontend hooks and components reach into the backend.

## Context

The codebase parser (GE-026) is conservative by design — it extracts `import` statements and nothing else. Network calls inside function bodies aren't touched. The OpenAPI parser (GE-006) knows nothing about the codebase. Both produce correct but isolated sub-graphs.

This user's codebase follows an unusually clean pattern (verified via investigation in the admin-dashboard project):

- ~95% of API calls go through `openapi-fetch`'s typed client as `client.METHOD('/literal/{path}')` where the path is **byte-identical** to the OpenAPI spec's path
- ~5% use raw `fetch(\`${config.API_BASE_URL}${path}\`)` as a legacy fallback
- API-layer files (`lib/api/**`) export `fetch*` / `post*` functions; hooks import those functions and call them inside `useQuery`/`useMutation` `queryFn`s

These patterns make extraction almost trivially accurate — no AST needed, no template-literal interpolation guessing, no runtime path construction.

## Scope

A new pure function `extractCodebaseApiLinks(input): ExtractResult` that takes a re-uploaded folder plus the current graph's codebase + API nodes and returns new `Link[]` to add.

### Extraction passes

**Pass 1 — Direct `client.METHOD(...)` calls.** Regex across every code file:
```
client\.(GET|POST|PUT|PATCH|DELETE|HEAD|OPTIONS)\s*\(\s*['"`]([^'"`]+)['"`]
```
Each hit produces a `(method, path)` pair. Match against existing API nodes whose `name` equals `${METHOD} ${path}` (the format the OpenAPI parser already uses). Emit edge: `codebase:file:<path> → openapi:op:<...>` with type `data_flow`, label `calls`.

**Pass 2 — Raw `fetch()` with template literal.** Regex:
```
fetch\s*\(\s*`\$\{[^}]+\}([^`]*)`
```
Captures the static path portion after the interpolation. Same matching logic. Catches config-based URL construction (`${config.API_BASE_URL}/admin/players/filter`).

**Pass 3 — Function-indirection via imports.** For each API-layer file (any file containing at least one `client.METHOD(...)` or raw-`fetch` call), build a map of `exportedFunctionName → endpoints it touches`. This is done via a forward-scan heuristic: between each `export (async )?function NAME` / `export const NAME =` declaration and the next export (or EOF), collect every `client.METHOD(...)` pattern. Over-connects slightly for files with multiple exports sharing helpers — acceptable for MVP.

Then for each NON-API-layer file, extract its imports that reference the API-layer files' functions, and check which of those imported names are called inside the file. Emit edges: `codebase:file:<importer> → openapi:op:<...>` for each endpoint reached through an imported-and-called function.

### Output

- Deterministic link IDs via existing `linkId(source, target, 'data_flow')` — rerunning produces byte-identical output
- All emitted links carry `origin: 'auto:codebase'`
- Links that already exist (by ID) in the current schema are deduplicated — the linker returns only NEW ones
- Paths in the code that don't match any API node in the current graph go into `warnings.unmatchedPaths` — useful for debugging spec/code drift

### UI

A new top-bar button "↔ Link imports" opens a dialog asking the user to re-select the codebase folder (file content isn't persisted after the initial import — we need it again for the regex passes). The dialog:

1. Reads the folder via `webkitdirectory` (reuses GE-026's file-read logic)
2. Runs the linker against the current schema
3. Shows a compact preview: total edges to be added, a list of the first ~20 `(sourceFile → METHOD /path)` pairs, plus any unmatched paths as a warning list
4. "Apply" button appends the new links to the schema (no merge engine needed — edges only add, never conflict)
5. "Cancel" discards

## Out of scope

- AST-based extraction (Babel / TypeScript compiler API). Regex is sufficient given how regular the openapi-fetch pattern is in this codebase. If users with messier codebases hit issues, file a follow-up.
- Multi-hop indirection (function → function → function → endpoint). Only one hop of indirection is resolved.
- Detecting which OTHER codebases a file makes HTTP calls to (cross-project linking). Single-project only.
- Dynamic URL construction that goes through helper functions (e.g. `buildUrl('players', id)`). Warn on these; leave to the user.

## Acceptance criteria

- Running the linker against a folder containing `client.GET('/admin/payments')` produces an edge from that file to the `GET /admin/payments` API node (when the node exists in the graph).
- Running against a hook file that imports `fetchPayments` from an API-layer file, which contains `client.GET('/admin/payments')`, produces an edge from the hook to the API node (indirect resolution).
- Rerunning the linker is idempotent — no duplicate edges.
- The preview shows accurate per-file extraction counts before the user confirms.
- The schema passes the v1.0 validator after apply.
- Unit tests cover: direct call, indirect call via imports, no match (unmatched path in warnings), multiple endpoints per file.

## Risks

- **Extraction false positives** — a comment or string containing `client.GET('/foo')` would be extracted. Low-risk in practice (regex will match it), and the consequence is one spurious edge; acceptable.
- **Over-connection from the forward-scan heuristic** — if an API-layer file has 5 exports and 5 endpoints but they don't line up 1:1 (e.g., helpers share endpoints), the importer-scan will attribute too liberally. The ticket explicitly accepts this trade-off in favor of not requiring an AST.
- **Re-selecting the folder is a UX friction point** — an alternative would be caching file content at codebase-import time, but hundreds of KB of JS bundled into localStorage per project isn't worth it. Re-selection is clear, honest, and one-time per run.

## Notes for the implementer

The file-resolution logic (`./foo` → `./foo.ts`, `@/bar` → `src/bar`, etc.) already exists in `src/importers/codebase/index.ts` as `resolveImport` + `trySuffixes`. Extract these into a helper module (`src/importers/codebase/resolve.ts`) and share between the codebase parser and the new linker.

The codebase parser should also get a new optional parameter to run the linker inline when called with a schema that already has OpenAPI ops. That covers the "import OpenAPI first, then codebase" flow without a separate user action.

Don't route the new links through the full merge engine. Emit them into a minimal candidate schema containing only the existing IDs plus the new edges, then filter-append in the handler. The merge engine's "auto is authoritative" rule would be actively harmful here since we don't want it to drop unrelated codebase entities.
