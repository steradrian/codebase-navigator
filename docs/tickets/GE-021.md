# GE-021 — Progressive / lazy subgraph loading

**Status:** TODO
**Phase:** Phase 3 — Scale
**Effort:** L
**Depends on:** GE-013, GE-020
**Blocks:** —

## Summary

Instead of loading the full graph at once, fetch only the subgraph relevant to the user's current view. As the user zooms, navigates, or expands clusters, additional subgraphs are fetched on demand.

## Context

At 10,000+ nodes, loading the full schema into the client is megabytes of JSON that block the initial render. Most of that data is irrelevant — the user only sees a handful of clusters at a time. Lazy loading is the correct answer, and the semantic zoom work (GE-013) makes it natural: fetch the top-level clusters up front, fetch a cluster's children only when it expands.

This ticket assumes GE-013 (semantic zoom) and GE-020 (server API) are in place.

## Scope

- On initial load, fetch only the top-level clusters (domain-level nodes) and their aggregate inter-cluster edges.
- When a cluster expands (per GE-013), fetch its children and their intra-cluster edges in a single request.
- Cache fetched subgraphs client-side keyed by cluster ID, so re-expanding a cluster is instant.
- Prefetch adjacent clusters when the user hovers over them, anticipating expansion.
- Search (GE-005) continues to work across the full graph — server-side search returns IDs, and the client resolves them by fetching the relevant subgraphs.
- Guided paths: when a path is activated, pre-fetch all clusters required to display the path at once. Do not fetch step-by-step.
- A visible indicator (subtle spinner or shimmer) shows when data is being fetched, so users know they are not looking at a stale view.

## Out of scope

- Client-side persistence / offline mode. Post-MVP.
- Speculative prefetching beyond hover prediction. Post-MVP.
- Server push of subgraph updates. That is GE-024.
- Eviction policies for the client cache — MVP can keep everything fetched in memory.

## Acceptance criteria

- Initial load for a 10,000-node graph completes in under a second on a reasonable connection.
- Expanding a cluster that has not been fetched yet completes within ~300ms.
- Re-expanding a previously-fetched cluster is instant.
- Search works against the full graph, not just loaded subgraphs.
- Guided paths display correctly without requiring the user to manually expand clusters.
- No unnecessary fetches — verifiable via the network tab.

## Risks

- Cluster-to-cluster aggregate edges must be correct even when only some clusters are expanded. The server API (GE-020) must be able to compute these at the appropriate granularity.
- Network latency dominates UX. Even a perfectly implemented lazy loader feels slow on a bad connection. Aggressive prefetching and optimistic expansion help.
- Cache invalidation — if a cluster is fetched and later mutated on the server (per GE-024), the client's cache must know. Either invalidate eagerly or subscribe.

## Notes for the implementer

This ticket is worth nothing without a large graph to test against. Before building, make sure a realistic 10,000-node test schema is available — either synthetic or imported from a real system. The UX only reveals its strengths and weaknesses at scale.
