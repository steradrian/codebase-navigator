# GE-115b — Entity propagation across the graph

**Status:** TODO
**Phase:** UX / data model
**Effort:** M
**Depends on:** GE-115 (catalog + API-side assignment), GE-026c (FE linker), GE-110 (BE linker)
**Blocks:** GE-111, GE-112, GE-113, GE-116

## Summary

After GE-115 tags API operations and database nodes with their entity/domain, run a propagation pass to tag FE and BE nodes that connect to them. A FE client function that calls `GET /admin/payments` inherits `entity: payment, domain: payment`. The hook wrapping that client function inherits it. The component using the hook inherits it. Infrastructure files (utils, pagination, index) that connect to many entities stay `Unclassified` — that's what makes them hubs.

## Context

With GE-115, entities exist only on API and database nodes. The rest of the graph (typically 80%+ of node count — every codebase file) has no entity until we propagate.

Propagation uses the cross-stack links the codebase linkers already create:
- GE-026c connects FE client functions to OpenAPI operations ("calls" edges).
- GE-110 connects BE handlers to OpenAPI operations ("implemented by" edges).
- Within the codebase graph, files link to the files they import (`dependency` edges).

We propagate entity along "flow" edges (calls, implemented by, and function-composition via imports when the importer is a domain file). We do NOT propagate along pure structural imports of utilities — otherwise `utils.ts` would inherit every entity it's imported by, which is both wrong and the source of the hub noise problem.

## Scope

### Propagation algorithm

Input: schema after GE-115 has run (API + DB nodes tagged).

1. **Seed set** = all nodes with `entity` set (from GE-115: API operations + database nodes).
2. **Pass 1 — BE handlers**: walk "implemented by" edges from each API operation. Each connected BE handler inherits `{ entity, domain }` from the operation. If a BE handler implements multiple operations with different entities, mark `entity = Unclassified`, keep the first domain (BE routers often serve one domain).
3. **Pass 2 — FE client functions**: walk "calls" edges from each API operation (edges created by GE-026c). Each FE client function inherits `{ entity, domain }` from the operation. Multi-operation clients → same multi-entity rule.
4. **Pass 3 — FE hooks and their consumers**: BFS outward from FE client functions along `dependency` edges IN REVERSE (the client function is imported BY hooks; hooks are imported BY components). Inherit only when:
   - The source node already has an entity (don't propagate empty).
   - The target node is a codebase node (don't cross back into API/DB).
   - The target node has no entity yet (don't overwrite a propagated tag).
5. If a target is reached from multiple sources with different entities, mark `entity = Unclassified` and keep only the domain if all sources agree on domain — otherwise unset domain too.
6. Do NOT traverse dependency edges in the forward direction (source imports target). A component importing `utils.ts` shouldn't push its entity onto utils. We only propagate from "this thing was called/implemented/wrapped" — the semantic direction.

### Hub detection (byproduct)

During propagation, track **how many distinct entities reach each node**. After the passes:
- Nodes where ≥ 3 distinct entities reached the node → `node.isHub = true`. Store as a computed property on the node for GE-112 to consume.
- This replaces degree-based hub detection from the GE-112 sketch with something semantically grounded: a hub is a cross-cutting infrastructure file, not just a high-degree node. Degree is a correlate; entity-span is the real signal.

### Schema field updates

- Add `Node.isHub?: boolean` — set during propagation, cleared on re-run. Not persisted as user intent, just a computed cache.
- Add a pass timestamp to `SchemaMeta.lastPropagationAt?: string` so downstream code can tell if a stored schema has been through propagation.

### When propagation runs

- After every OpenAPI import (terminal step, after merge).
- After every codebase import (terminal step, after merge + linker).
- After every schema-load upgrade (`upgradeLoadedSchema`) that detects `meta.lastPropagationAt` is absent or older than `meta.lastUpdated`.
- Explicitly triggerable via the review dialog (GE-116) "Re-tag nodes" button.

### Manual override respect

Any node with `manualOverrides: ['entity']` is untouchable by propagation. The user's choice wins. Log a skip count in dev mode.

## Out of scope

- Confidence scoring per tag ("95% sure this is `payment`"). Binary for MVP.
- Propagation across language boundaries inside the codebase (e.g. Go handler importing a Go utility). Only the three stated edge types. Other patterns wait for real workloads.
- Updating `isHub` live as the user edits the schema. Recompute on next full propagation run.
- Cross-entity propagation priority (e.g. "payment is more important than auth"). All entities are equal; conflicts yield Unclassified.

## Acceptance criteria

- On the admin-dashboard graph: FE files like `usePayments`, `fetchPayments`, `PaymentsTable` all carry `entity: payment`. Without invoking the extractor's filename heuristic (verify by deleting the filename extractor).
- Utility files (`utils.ts`, `pagination.ts`, `client.ts`) have no entity set after propagation. They carry `isHub: true`.
- BE Go handler `handlers/payments/list.go` carries `entity: payment, domain: payment` (inherited from the operation it implements).
- The review dialog (once GE-116 ships) shows the Unclassified bucket containing exactly the infrastructure files, not `string` / `signup` / `option` noise from before.
- Running propagation twice in a row is a no-op (idempotent).
- A user manually setting `entity: 'something'` on a node via the catalog editor persists across the next propagation.
- Re-importing the OpenAPI spec (which triggers propagation) doesn't produce diff noise on unchanged codebase nodes.

## Risks

- **Propagation over-reach**: a single cross-dependency (e.g. `auth` middleware called by every domain handler) could spread `auth` across the whole backend. Mitigation: the multi-entity → Unclassified rule kicks in — auth middleware would be reached by handlers tagged `payment` AND `customer` AND `bonus`, lands as Unclassified + Hub. Verify in tests.
- **Direction-sensitive reverse-BFS is easy to get wrong**. Dependency edges are directed (A imports B). We propagate along `target → source` of a dependency (B's entity flows to A if A depends on B AND B is a leaf with an entity). Easy to flip by accident. Name the helper explicitly: `propagateAlongDependencyInverse`.
- **Performance on 10k+ node graphs**: propagation is BFS, O(nodes + edges). A batched Map-based frontier is fine. Don't use recursion; don't copy the schema per node. Mutate a working copy of `nodes[]` once at the end.
- **`isHub` vs GE-112's degree-based marker**: GE-112 originally defined hubs by degree p95. This ticket redefines hubs by entity-span (≥ 3 entities reach the node). Update GE-112's acceptance criteria to use `node.isHub` instead of recomputing from degree. File note in GE-112.

## Notes for the implementer

Put propagation in `src/schema/entity/propagate.ts`. Single exported function:

```
propagateEntities(schema: Schema): Schema
```

Returns a new schema (pure function). Internally uses mutable working maps for speed, but doesn't leak them.

Edge lookup: build two adjacency maps once at the top of the function — `byType: Map<linkType, Array<{ source, target }>>` and `byNode: Map<nodeId, Array<Link>>`. Reuse across passes.

Write unit tests against a small hand-crafted schema with the three edge types present, including:
- Happy path: one entity propagates along a three-link chain.
- Conflict: node reached from two entities → Unclassified + Hub.
- Manual override: node with `manualOverrides: ['entity']` is skipped.
- Cycle: A depends on B which depends on A. No infinite loop.
- Leaf hub: a utility imported by 5 domain files → stays Unclassified + Hub (the reverse BFS doesn't push entities onto it because the edge is the "wrong" direction for flow propagation).

The last test case is the crux — verify that the multi-domain ancestor of a hub doesn't accidentally pollute the hub's tag via reverse propagation. The rule is: flow goes from source of a call/implementation edge to its users. A utility file is a dependency target (source imports it), never a flow source.
