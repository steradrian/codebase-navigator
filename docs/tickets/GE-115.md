# GE-115 — Closed-vocabulary entity + domain catalog from OpenAPI

**Status:** TODO
**Phase:** UX / data model
**Effort:** M
**Depends on:** GE-006 (OpenAPI parser), GE-103 (entity field on Node)
**Blocks:** GE-115b, GE-116, GE-104b, GE-111, GE-112, GE-113

## Summary

Replace the open-vocabulary heuristic extractor with a closed-vocabulary catalog derived from the OpenAPI spec itself. **Entity** = a normalized `components.schemas` entry (minus wrappers, value objects, and enums). **Domain** = an OpenAPI `tag`. Every API operation node carries both. Every database node (created from a schema) carries the entity it represents. Files can no longer invent new entities from folder names or filenames.

## Context

The previous extractor surfaced 93 "entities" on a real 615-node graph — roughly 70 of them noise (`string`, `query`, `setup`, `signup`, `path`, `option`, etc.) pulled from weak signals (filenames, path segments) on files with generic names.

Real entities are a closed set: they're the `components.schemas` entries in the spec — the domain objects the API actually exchanges. Looking at the admin-dashboard spec, that's ~15 entities (`customer`, `payment`, `bonus`, `freespin-bonus`, `rakeback`, `game`, `category`, `round`, `comp-point`, `document`, `tag`, `account`, `payment-system`, `payment-provider`, and a few borderline types).

On top of that, OpenAPI `tags` already group operations by coarse domain (`Customer`, `Wallet`, `Payments`, `Aggregator`, `Bonus`, `Auth`). We keep both — domain for "the whole slice of the system," entity for "the specific thing flowing through."

This ticket covers catalog + extraction at the OpenAPI parse boundary. Propagation through the rest of the graph is GE-115b.

## Scope

### Data model changes

- `Node.domain?: string` — new optional field. Kebab-case singular, matches one entry in `schema.meta.domains`.
- `SchemaMeta.domains?: string[]` — canonical list of domains present in the schema (paralleling `meta.entities`).
- `Node.entity` semantics tighten: only set if the node matches a catalog entry. No more open-vocabulary values.
- `SCHEMA_VERSION` bumps to `1.2`.

### Catalog construction during OpenAPI import

Build the catalog in two passes over the spec:

**Pass 1 — domain catalog**:
- Every entry in `spec.tags` becomes a domain. Normalize: lowercase, kebab-case, singular. `Customer` → `customer`, `Payments` → `payment`, `Types` → skip (structural, not domain).
- If an operation has no `tags`, bucket as `Unclassified` domain (not stored — just absent `domain` on the node).

**Pass 2 — entity catalog**:
- Walk `components.schemas`. For each schema, decide: entity, value object, or skip.
- **Skip** if:
  - Pure enum (`type: string` + `enum: [...]`, no other properties).
  - Name ends in `Request`, `Response`, `Dto`, `Params`, `Options` (request/response wrappers).
  - Name is one of: `PageInfo`, `Error`, `ProblemDetails`, `CurrencyCode` (transport primitives — maintain a short hard-coded list).
- **Collapse via allOf / oneOf**:
  - If schema is `allOf: [{ $ref: X }, …]`, inherit X's entity identity.
  - If schema is `oneOf: [X, Y, …]` and all variants share a common ancestor (via allOf), use the ancestor. Otherwise tag as the first variant's entity.
  - Example from the spec: `AdminCashout` allOf-extends `AdminPayment` → both are `payment`. `AdminPaymentItem` oneOf `[AdminCashout, AdminDeposit]` → common ancestor `AdminPayment` → `payment`.
- **Value object detection**: after the above, any schema that is **only referenced from inside other schemas' properties** (never the direct payload of a response body or request body) is a value object. Skip. Examples: `Amount`, `ExchangeAmount`, `BonusConditions`, `PaymentSystemCurrencyLimit`, `UserMetadata`.
- **Normalize remaining names**:
  - Strip `Admin` prefix: `AdminPayment` → `Payment`, `AdminBonusIssue` → `BonusIssue`.
  - Convert to kebab-case singular: `BonusIssue` → `bonus-issue`, `FreespinBonus` → `freespin-bonus`.
  - Apply existing `singularize()` logic for the trailing noun.
- **Deduplicate**: multiple schemas collapsing to the same normalized name become one catalog entry (e.g. `Bonus` and `BonusRequest` both map to `bonus`).
- Persist the final list to `schema.meta.entities`.

### Assignment during OpenAPI import

**Database nodes** (created from schemas):
- Each database node is born from a specific schema. Its entity = the normalized name of that schema (after collapse). If the schema was filtered (value object / enum / wrapper), no database node is created for it (matches current behavior for enums; new behavior for wrappers and value objects — they don't deserve nodes).
- No domain on database nodes (databases serve multiple domains).

**API operation nodes** (one per path/method):
- `domain` = first entry in the operation's `tags`, normalized.
- `entity` = determined by response/request unwrap (see below). If unwrap fails or the target schema was filtered, leave `entity` unset and log a warning at import time.

### Response / request unwrap algorithm

For each operation:

1. Pick the success response: prefer `200`, then `201`, then the first `2xx`.
2. Get `content["application/json"].schema`.
3. Attempt unwrap, in order:
   - Schema is `$ref` → the referenced schema is the target.
   - Schema is `object` with `properties.data.$ref` → the data ref is the target.
   - Schema is `object` with `properties.data.type === 'array'` and `properties.data.items.$ref` → the items ref is the target.
4. If unwrap failed or target was filtered:
   - For mutations (POST/PUT/PATCH/DELETE): retry steps 2–3 against `requestBody.content["application/json"].schema`.
   - Otherwise fall back to the operation's `tag` (so `POST /admin/sign_up` → `entity = 'auth'` because the tag is `Auth` and the response is a `TokenResponse` we can't resolve).
5. If still no target: `entity` remains unset.

External `$ref` handling: if a `$ref` points outside the current document (another URL or file), extract the final fragment segment as the schema name (`/components/schemas/PageInfo` → `PageInfo`) and apply the catalog filter. `PageInfo` / `ProblemDetails` / `Error` end up filtered, so the operation falls through to step 4.

### Deprecations

- Remove the filename-based and folder-based extractors from `entity/extractor.ts` (`fromCodebasePath`, `fromCodebaseFilename`). Codebase nodes get their entity only via propagation (GE-115b), not extraction.
- Remove the OpenAPI-path extractor (`fromOpenApiPath`). The unwrap-based assignment replaces it.
- Keep `extractEntity` around as a thin wrapper, but it now only returns values for manually-overridden nodes. Everything else flows from the catalog + unwrap path.
- The legacy `backfillEntities()` on load (GE-114) is retained but internally re-runs the new extractor. Existing stored graphs get re-tagged on next load; bump of `SCHEMA_VERSION` to `1.2` triggers this.

## Out of scope

- Propagation to codebase nodes. That's GE-115b.
- Review dialog rewrite. That's GE-116.
- Filter rail domain facet. That's GE-104b.
- DB schema parser as an alternative catalog source. That's GE-117 (deferred).
- User-editable "never treat as entity" stoplist in the UI. The hard-coded filters + user merge/delete in GE-116 cover MVP.

## Acceptance criteria

- Import the admin-dashboard spec. `schema.meta.entities` contains ~15 entries (the set in the Context section). No entries for `string`, `sign-up`, `sign-in`, `path`, `option`, `query`, `setup`, `tag` (the UI-component sense), etc.
- `schema.meta.domains` contains: `customer`, `wallet`, `payment`, `aggregator`, `bonus`, `auth`. Not `types` (filtered).
- Every `api`-type node has `domain` set (or `Unclassified` if the operation lacks tags).
- Every `api`-type node that returns a domain object has `entity` set correctly. `GET /admin/players/{id}/payments` → `entity = 'payment'` (from `AdminPaymentItem` → `AdminPayment` → normalize). `GET /admin/players` → `entity = 'customer'`. `POST /admin/sign_up` → `entity = 'auth'` (fallback to tag).
- Every `database`-type node's entity matches its source schema (normalized). No database nodes created for filtered schemas (`Amount`, `ExchangeAmount`, `PageInfo`, etc.).
- Re-import the same spec → merge engine reconciles without duplicating nodes or creating phantom entities.
- A stored graph at `SCHEMA_VERSION=1.1` loads, gets upgraded to `1.2` via `upgradeLoadedSchema`, and shows the new closed-vocabulary catalog on the next render.

## Risks

- **Schemas without a `$ref` path to any response/request**: some operations return inline shapes only. The tag fallback covers this, but if the tag is `Types` (filtered) or absent, the node ends up with no entity. Acceptable — these are rare and show up as "Unclassified" in the review UI.
- **`allOf` / `oneOf` resolution is a mini graph problem**: shallow implementation first (one level of indirection). If a schema allOf's another schema that allOf's a third, keep walking until you hit a concrete parent. Add a cycle guard.
- **Value-object detection depends on spec scan completeness**: the rule "only referenced from inside other schemas" requires walking every schema before deciding. Make it a second pass after the initial catalog. Don't gate entity assignment on this — if a value object accidentally becomes an entity in edge cases (a schema that both represents an entity AND is nested somewhere), the review dialog lets the user delete it.
- **Name collisions after normalization**: `Admin*` prefix stripping + singularization can collide (`AdminPayment` and `Payment` both → `payment`). Desired behavior — they ARE the same entity. The merge is intentional. Test this case.
- **External `$ref`s** (the `lucky:gains@api.kong.io` refs in the spec): treat as opaque. Extract the leaf schema name from the ref's fragment, apply catalog filter, otherwise fall through. Do not attempt to fetch the external doc.
- **Backward compatibility for projects with stored v1.1 entities**: `backfillEntities` now ignores the old entity value on existing nodes and re-derives from the catalog. Users who manually set `entity` via the review UI before GE-115 ships could have their choices overwritten. Mitigation: preserve `entity` on nodes that have `manualOverrides: ['entity']`. That flag already exists.

## Notes for the implementer

Split the work into three pure functions, each testable in isolation:

1. `buildEntityCatalog(spec): { entities: CatalogEntry[], domains: string[] }` — pass over `components.schemas` + `tags`, applies filters + normalization.
2. `resolveOperationEntity(operation, spec, catalog): { entity?: string, domain?: string }` — unwrap + fallback.
3. `normalizeSchemaName(raw): string | null` — returns null if filtered, else the canonical name.

Put them in `src/schema/entity/catalog.ts`. The existing `src/schema/entity/extractor.ts` becomes a thin shim that delegates to the catalog functions plus the manual-override check.

The test fixture should include the admin-dashboard spec (or a representative subset) — the allOf/oneOf case, the standard `{ data }` wrapper, the list case, the direct-ref case, the auth inline-schema case, and an external `$ref`. Every response shape in the spec should be covered.

Update the existing `backfillEntities` tests to reflect the new closed vocabulary — several old tests assert open-vocabulary behavior that's going away.
