# GE-102 — Hover tooltips on nodes

**Status:** DONE
**Phase:** Polish / UX
**Effort:** S
**Depends on:** —
**Blocks:** —

## Summary

When the mouse hovers over a node, show a floating tooltip with the node's name, type, group, and (once GE-103 lands) entity. Users can scan the graph for the node they want without committing to a click.

## Context

Today discovery requires selection. If you want to know what a given glowing dot IS, you have to click it — which moves the camera, updates the panel, pushes to history (post-GE-101). Users find this expensive and end up avoiding exploration. A hover-read mechanism is the smallest possible change to make the graph browsable.

## Scope

- On `mousemove` over the canvas (throttled to roughly every other frame), raycast to find the nearest node under the cursor.
- If a node is hit, show a DOM tooltip positioned near the cursor (offset ~16px right and down) containing:
  - Node name (prominent)
  - Type label with the type's color dot
  - Group (if present)
  - Entity (if present — post GE-103)
  - Origin tag (manual / auto:openapi / auto:codebase) as a small muted pill
- Tooltip hides when the cursor leaves a node or exits the canvas.
- Tooltip DOES NOT disable the existing click-to-select behavior — it's purely additive.
- Cursor changes to `pointer` when hovering a node, `grab` / `grabbing` during drag, `default` otherwise.
- Respects the existing visibility rules — hovering a collapsed cluster's child (which is invisible) doesn't produce a tooltip because the raycaster only tests visible meshes.

## Out of scope

- Tooltips for edges. Hovering a link line to see its label is nice-to-have; defer.
- Rich tooltips with the full description. Keep it compact — if the user wants more, they click.
- Touch equivalents (long-press to peek). Desktop/mouse only for MVP.

## Acceptance criteria

- Moving the cursor over any visible node shows the tooltip within one frame.
- Tooltip shows the correct name, type, group (if set), entity (if set).
- Tooltip does not flicker when moving between adjacent nodes — it transitions smoothly or dismisses between them.
- Moving off the canvas hides the tooltip immediately.
- Hover works in all modes (idle, selection, path, blast, diff).

## Risks

- Raycasting on every mousemove is expensive on large graphs. Throttle via `requestAnimationFrame` — at most one raycast per frame.
- Tooltip positioning near the viewport edge must flip to avoid clipping. Use simple `right: <px>` / `bottom: <px>` fallbacks when cursor is near the right or bottom edge.
- The existing drag-to-orbit handler sets `cursor: grabbing` during drag. Don't let hover tooltips conflict — suppress the tooltip while `mouseRef.current.down === true`.

## Notes for the implementer

Keep the tooltip a plain absolutely-positioned DOM element rendered inside the main return tree, not inside Three.js (sprites won't give pixel-accurate positioning near the cursor). Update position via a ref-driven imperative style update, not React state, so per-frame moves don't trigger re-renders.
