# GE-026 — Codebase parser (AST → graph)

**Status:** DONE
**Phase:** Phase 4 — Ecosystem
**Effort:** L
**Depends on:** GE-003, GE-007
**Blocks:** —

## Summary

Walk the AST of a TypeScript / JavaScript codebase to extract modules, routes, API calls, and component imports. Translate into graph nodes and links via the same candidate-schema contract used by the OpenAPI importer.

## Context

OpenAPI covers the backend surface but not the frontend. A user asking "how does the checkout flow work?" benefits from seeing the frontend components, their routes, their data dependencies, and how they connect to backend endpoints. The codebase parser fills that gap.

This is a large ticket. Ambition is proportional to scope — a narrower first pass (e.g., "Next.js routes + fetch calls") is acceptable, with broader language / framework coverage as follow-ups.

## Scope

For a first pass targeting a single framework (recommended: Next.js App Router):

- Walk the project's file tree, identifying pages, layouts, and API routes from the framework's conventions.
- Parse each file's AST to extract:
  - Component imports (directed graph of component-to-component dependencies).
  - Network calls (`fetch`, `axios`, typed API clients) — identify the endpoint they target and create a link from the component node to the corresponding API node (if present in the current schema from GE-006).
  - Top-level file exports (to name component nodes).
- Emit nodes (UI type for components, Page type for routes) and links (dependency for imports, data_flow for API calls).
- Every node and link carries `origin: "auto:codebase"`.
- Deterministic IDs so re-parsing produces identical output.
- Integration with the merge engine (GE-007) via the same candidate-schema contract as GE-006.
- Configuration file at the target project's root specifying the framework, root directory, and ignore patterns.

## Out of scope

- Full language support (Python, Go, Rust). Pick one language / framework and get it right; expand later.
- Runtime analysis (instrumenting code to observe actual calls). Static only.
- Inferring business logic from code (what the component actually does). Purely structural.
- Visual rendering of code-level detail (lines of code per component, cyclomatic complexity). Node metadata can carry these, but MVP does not display them.
- Integrations with type checkers or language servers (e.g., pulling types directly from TypeScript's compiler API). Use a plain AST parser; keep it portable.

## Acceptance criteria

- Running the parser against a medium-sized Next.js project produces a schema with the right shape of component and route nodes.
- Re-running produces identical output (determinism).
- Links to API nodes correctly resolve when the OpenAPI import is also in play.
- Unit tests cover representative file shapes: client component, server component, route handler, nested import.
- The parser fails gracefully on files it cannot parse (log a warning, skip the file, never crash the whole run).

## Risks

- Scope explosion. Every framework has quirks. Pick one and document what is and is not supported. Do not try to cover Vue, Svelte, Remix, and Next in v1.
- AST parsing is slow on large codebases. Budget parse time and parallelize.
- Dependency resolution across tsconfig paths, aliases, monorepos is messy. Rely on the project's own tsconfig where possible.

## Notes for the implementer

Start with the narrowest useful scope — Next.js App Router pages + fetch calls. Prove the value, ship it, then extend. Resist the temptation to build a language-agnostic AST walker — you will never finish.
