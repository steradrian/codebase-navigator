# GE-018 — Web Worker physics (Barnes-Hut)

**Status:** PARTIAL — Barnes-Hut landed; worker deferred (see resolution notes)
**Phase:** Phase 3 — Scale
**Effort:** M
**Depends on:** GE-001
**Blocks:** GE-019 indirectly (both are needed for 1000+ nodes)

## Summary

Move the force simulation off the main thread into a Web Worker, and replace the O(n²) pairwise repulsion with a Barnes-Hut octree approximation (O(n log n)). Together, these unlock graphs up to the low thousands of nodes at interactive framerates.

## Context

The current simulation computes repulsion between every pair of nodes on every tick. At 100 nodes this is fine; at 1,000 it is 499,500 comparisons per tick and the tab becomes unresponsive. The simulation also runs on the main thread, so even when it is not too slow to complete, it steals frame budget from rendering and UI.

Two optimizations solve this:

1. **Barnes-Hut** — approximate clusters of distant nodes as a single point-mass at their center of gravity, collapsing repulsion from O(n²) to O(n log n).
2. **Web Worker** — move all of the simulation's math off the main thread. Main thread only reads position buffers to render, keeping UI and rendering smooth regardless of graph size.

The existing `ForceSim3D` is already a pure class with no DOM dependencies, which makes the worker move straightforward.

## Scope

- Relocate `ForceSim3D` into a Web Worker. Main thread posts the initial graph; worker runs the simulation loop; worker posts position updates to main thread on a throttled cadence.
- Use `SharedArrayBuffer` + `Atomics` for position transfer when available. Fall back to structured-clone message passing if SharedArrayBuffer is unavailable (cross-origin isolation headers missing, etc.). Document the fallback.
- Replace pairwise repulsion with a Barnes-Hut octree implementation. The `theta` parameter (approximation threshold) should be configurable; default to 0.8 or so.
- Preserve all existing simulation parameters (attraction, centering, damping, group cohesion). These continue to apply.
- The main thread's render loop reads position buffers each frame and updates node mesh positions. No physics math runs on the main thread.
- Drag-to-reposition (if it exists) posts updates back to the worker.

## Out of scope

- GPU-based simulation (WebGPU compute shaders). That is the next step beyond this ticket, for 10,000+ nodes.
- Replacing the force simulation with a completely different layout algorithm. Stick with force-directed.
- Integrating an external physics library (ngraph, d3-force-3d). The current engine is compact and under our control — keep it.
- Multiple simulation workers for very large graphs. One worker per graph for MVP.

## Acceptance criteria

- On a graph of 500 nodes, framerate is stable at 60fps while the simulation is active (hot reheat after drag, etc.).
- On a graph of 2,000 nodes, framerate remains interactive (30fps+) with reasonable convergence times.
- Simulation math does not run on the main thread — verifiable by main-thread profiling during simulation.
- No functional regressions at small scale (25-node demo behaves identically to pre-worker version).
- Barnes-Hut implementation is covered by unit tests (tree construction, force approximation against exact pairwise on small inputs).

## Risks

- `SharedArrayBuffer` requires cross-origin isolation (COOP + COEP headers). Document the deployment requirement. Fallback must work if headers are missing.
- Worker lifecycle management (create, dispose, recreate on schema change) is easy to get subtly wrong. Clean up aggressively.
- Barnes-Hut correctness is subtle — nodes can end up in wrong octants, forces can be miscomputed for edge cases (empty cells, singletons). Test thoroughly.
- The MVP demo graphs are small enough that this ticket delivers no visible benefit at their scale. Validate perf wins against a large synthetic graph.

## Notes for the implementer

Get the Barnes-Hut implementation correct against exact pairwise forces on small graphs before scaling up — silent divergence is hard to debug. Use the existing `ForceSim3D` as the reference implementation for correctness.

## Resolution notes

**Shipped**: Barnes-Hut repulsion in `ForceSim3D` as an optional path. Auto-enables when `nodes.length > 60`; explicit `useBarnesHut: boolean | undefined` on the sim lets tests pin behavior. Theta defaults to 0.8, tunable via `sim.theta`. Octree builds from a bounding cube over all node positions, aggregates center-of-mass on insert, and traverses per-target with the standard Barnes-Hut criterion (`size² / distance² < theta²`). Correctness tested against the exact O(n²) implementation on a 30-node cluster — velocity magnitudes agree within ~25% (expected tolerance at theta=0.8). Also tested: empty and single-node graphs don't crash.

**Deferred as follow-up (GE-018b)**: Web Worker wrap of the simulation. Rationale: the worker refactor changes the main thread's render loop contract significantly (synchronous `sim.tick()` becomes async; node-position reads go through a snapshot buffer or structured-clone messages), and at MVP graph sizes (≤ 200 nodes) Barnes-Hut alone keeps the main thread responsive. File a new ticket when a user's graph hits the 500+ node scale and the main-thread simulation becomes a real bottleneck.

**Not shipped**: `SharedArrayBuffer` + cross-origin isolation headers. Tied to the worker deferral — revisit with the worker ticket.
