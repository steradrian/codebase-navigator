# GE-029 — Natural language queries

**Status:** DONE
**Phase:** Phase 4 — Ecosystem
**Effort:** M
**Depends on:** GE-003, GE-017
**Blocks:** —

## Summary

A search surface that accepts free-form natural language ("show me everything that touches payments") and resolves it into graph operations — filters, highlights, path activations, or blast-radius invocations — via an LLM.

## Context

Node search is fine for users who know what they are looking for. Most users do not. "Show me the payment flow" or "what breaks if the search service goes down" are questions users want to ask without learning the tool's structure. LLM-mediated query resolution is the natural UX for that.

This ticket is a stretch feature — valuable, but dependent on LLM quality and the underlying primitives working well. Keep scope tight.

## Scope

- A natural-language input surface (prominent search bar with a hint like "Ask anything").
- The query is sent to an LLM along with a structured description of the available graph operations (search, filter by type / group / owner, highlight, activate guided path, blast radius, focus camera).
- The LLM responds with a structured action or sequence of actions — not free text. Use a function-calling / tool-use pattern with a fixed schema so outputs are deterministic and applicable.
- The client executes the returned actions, updating view state accordingly.
- Unrecognized or ambiguous queries prompt the user for clarification rather than guessing.
- A subtle visual trail — "showing: X because you asked Y" — keeps users oriented and lets them recover if the LLM misunderstood.

## Out of scope

- Generating new nodes, links, or paths from queries. Read-only for MVP.
- Multi-turn dialog beyond clarification. Single query, single response.
- Fine-tuned models or custom routing. Use a general-purpose frontier model.
- Voice input. Post-MVP.

## Acceptance criteria

- A user can ask a realistic question ("what uses the users table?") and see the graph respond correctly most of the time.
- Failure modes are graceful — the system admits it does not understand rather than lighting up the whole graph.
- The visual trail makes it clear why the current view was chosen.
- Response time is under a few seconds in common cases.
- API errors do not leave the view in a broken state.

## Risks

- LLM non-determinism. The same query may produce different actions across runs. Tune the prompt and the function schema to minimize this.
- Quality is subject to model capability. Run a benchmark of common queries against the model and iterate.
- Cost — every query is an API call. Set per-session limits or require user confirmation for expensive follow-ups.
- Prompt injection through crafted queries. Sanitize outputs; never execute returned code directly — only map to the fixed action schema.

## Notes for the implementer

The action schema is the contract. Define it carefully — a narrow, well-documented schema produces consistent LLM behavior; a loose one produces chaos. Test against a curated set of real user questions from day one.
