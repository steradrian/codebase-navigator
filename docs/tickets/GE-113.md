## Summary

Above the connection list, render a row of entity chips — one per entity the selected node touches (via its direct peers). Clicking a chip scopes the graph to that entity's subgraph **relative to this node**: the node itself, its peers in that entity, and transitively what those peers touch within the same entity. Answers the question "I'm on this file — show me only its Payment connections."

## Context

User's original framing: "If we trigger the entity flow is that the solution? Can we trigger seeing any entity flow from this file/node?" The filter rail (GE-104) already lets users scope globally by entity. What's missing is the common case: you're on a hub or a client file, you want to see its slice of ONE entity, not the whole app's slice.

Evidence: on `Ann test`, 10 hubs touch 11+ entities and the median hub touches 9. Without a per-node entity pivot, hubs are either (a) a wall of peers or (b) filtered down to the whole-app entity slice which includes nodes that have nothing to do with this particular hub.

## Scope

- Selected node's INFO panel gets a "Entity lens" row between the entity chip (self) and the connection sections.
- Compute the set of entities appearing across the selected node's direct peers, excluding the selected node's own entity. Sort by peer count descending.
- Render as a chip row: `● Payment (8) · ● Bonus (6) · ● Auth (4)`. Active chip is filled; inactive is outlined.
- Clicking a chip activates the entity lens. Clicking the active chip deactivates it. Only one entity lens active at a time.
- Active lens behavior:
  - The graph dims everything outside the "ego subgraph in this entity": start from the selected node, traverse peers whose `entity === lens`, traverse THEIR peers whose `entity === lens`, continue until no new nodes added. Depth is unbounded but naturally bounded by the entity's size.
  - The selected node itself stays bright regardless of its own entity.
  - Connection sections filter to only rows in the lens subgraph. Sections with 0 rows in the lens are hidden.
  - Lens is distinct from the filter rail — rail filters apply first (a node not in the rail's allow-set is dimmed even if in the lens subgraph). If both are set, the intersection wins.
- Deselecting the node clears the lens. Navigating via back/forward preserves the lens if the new node also touches that entity; otherwise clears it.
- URL state (GE-022): include the active lens entity so shared links preserve it.

## Out of scope

- Multi-entity lens (A ∩ B or A ∪ B from the same node). If needed, use the global filter rail.
- Persisting lens state across sessions beyond URL.
- A "show all entities this node touches indirectly" expansion. We only show entities of direct peers — keeps the chip row small and obviously the-first-neighborhood.

## Acceptance criteria

- Select `utils` (hub, touches many entities). Entity lens row shows chips for each entity its peers belong to, sorted by count.
- Click `Payment`. Graph dims everything outside utils + its Payment-entity peers + their Payment-entity peers (transitively). Connection panel shows only Payment rows.
- Click the active chip. Lens clears, graph returns to normal.
- Click a different chip. Lens switches atomically (no flicker of the previous lens).
- Select a different node. Lens row updates to the new node's entity neighborhood. If the previous lens entity isn't present, it clears.
- Combine with filter rail: enabling a rail filter for type=ui while Payment lens is active shows only ui-typed Payment nodes in utils's ego.
- URL round-trips with the lens active.

## Risks

- Traversal can be expensive on dense graphs. Cap at a sensible node budget (say 5000 traversed) and bail with a warning in dev; in prod, let it run. The `Ann test` graph is 615 nodes — a full BFS is nothing.
- Users may confuse "lens" (per-node entity pivot) with "filter rail entity filter" (global scope). The chip-row UI has to feel different — shape, placement, and the fact that it's INSIDE the info panel should communicate that.
- Interaction with blast radius: if blast is active from the selected node, the lens should scope the blast's severity propagation to only lens nodes. Test this case explicitly.

## Notes for the implementer

The dim decision in the animation loop becomes: `isInLensSubgraph(node) ? fullBrightness : heavyDim`. Combine with the existing filter / selection / path / blast stack — lens is one more outer check, same shape as filter.
